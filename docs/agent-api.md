# ANet Relay Agent API

English · [简体中文](agent-api.zh-CN.md)

ANet Relay exposes the fleet it flies to external programs: scripts, autonomous agents and language models. This guide covers the control model, the REST and WebSocket interface (flight, device and application levels), the Python SDK and the three MCP servers. The reference for every endpoint and model is generated by the running backend at `http://127.0.0.1:8765/docs` (OpenAPI at `/openapi.json`).

> **Safety.** Code written against simulators runs unchanged on real aircraft; only the vehicle id differs. Fly real aircraft only inside a netted area with a padded floor, with an operator at the Relay window who can take over or stop at any time.

## 1. Quick start (no hardware)

1. Start Relay. In the desktop app, click **Add sim** at the bottom of the fleet bar. From a source checkout you can run the backend alone: `.venv/bin/python -m relay --dev` (the operator token is printed once on stderr).
2. Fly a simulator with the Python SDK (standard library only, Python 3.10 or later):

```python
import sys
sys.path.insert(0, "sdk/python")            # or copy anet_relay_client.py next to your script
from anet_relay_client import RelayClient

with RelayClient() as relay:                # http://127.0.0.1:8765, or $RELAY_API
    relay.open_session("my-agent")          # the lease renews in the background
    relay.claim("sim-1")
    relay.takeoff("sim-1", alt=1.2)         # blocks until the skill finishes
    relay.goto("sim-1", 0.5, 0.5, 1.2)
    relay.land("sim-1")
```

3. Or connect a language model through MCP (section 8): one server each for flight, device-level and application control.

The six examples in `sdk/python/examples/` run against simulators:

| Example | What it does |
|---|---|
| `hover_sim.py` | Claim, arm, take off to 1.2 m, hover 8 s, land, release |
| `watch_handback.py` | Fly circles on sim-1; pause when a person possesses it; continue from the current position after `relay_handback` |
| `course_sim.py` | Fly the `cage-loop` ring course ring by ring with `goto` and print the result |
| `swarm_square.py` | Four simulators take off together, fly a synchronised square rotation and land |
| `bench_routine.py` | Take off, hover, forward 1 m, back 1 m, turn 45° and land as one plan |
| `device_tour.py` | Device overview, raw command catalogue, single-motor tests and an `attitude` hold |

Each example accepts `--base` and `--name`. With `--operator-token` (or `$RELAY_OPERATOR_TOKEN`) the examples add missing simulators themselves; otherwise add them in the app (**Add sim**).

## 2. Control model

Relay is a relay of control between people and agents. Every aircraft has at most one controller at a time.

| Term | Meaning |
|---|---|
| **Session** | An agent identity. `POST /sessions {name}` returns a token and a lease (15 s). Any authenticated call renews the lease; `POST /sessions/heartbeat` renews it explicitly. An expired session loses its claims and its stick streams stop within 0.2 s. |
| **Claim** | A session's right to control an aircraft (`POST /vehicles/{id}/claim`). One claim per aircraft; claiming an aircraft held by another live session fails with `claimed_by_other`. |
| **Possession** | An operator flying the aircraft from the Relay window (keyboard, on-screen sticks or a gamepad). Possession always wins: it stops the agent's skill and sticks and **suspends** the claim. While suspended, every control call fails with `possessed_by_human` or `claim_suspended`. |
| **Hand-back** | When the operator releases, a live suspended claim becomes active again and Relay emits `relay_handback`. Relay sends nothing to the aircraft at that moment; the agent decides what happens next. |
| **Stop** | Emergency stop (`POST /vehicles/{id}/stop`): zero throttle for 50 ms, then a disarm request. It never changes who controls the aircraft. |

The `controller` field of each vehicle is `none`, `human` or `agent`.

An agent should therefore treat `possessed_by_human` and `claim_suspended` as "pause", watch the events for `relay_handback`, and re-read the vehicle state before continuing. `watch_handback.py` shows the pattern.

### Control levels and capabilities

| Level | Interface | Requires capability |
|---|---|---|
| 1 | `sticks` (roll, pitch, yaw, throttle) | `manual` (an autopilot heartbeat) |
| 2 | `arm`, `mode`, skills `takeoff`, `land`, `hold`, `move`, `yaw`; plans | `althold` for takeoff, hold, move and yaw |
| 3 | skills `goto`, `rtl`, ring courses; closed-loop `move` | `position` (a fresh local position estimate) |

Every vehicle reports `capabilities: {manual, althold, position}`. A missing capability fails with `capability_missing` or `no_position_estimate`. Simulators have all three. Real aircraft report `position` only with a local position source such as optical flow, motion capture or UWB.

## 3. Frames and units

- **Position:** metres, East-North-Up: `x` east, `y` north, `z` up. All simulators share the frame `sim` (each spawns at a different grid point). Each real aircraft reports its own `local` frame, with its origin where the autopilot initialised its estimator.
- **Attitude:** radians; roll right-wing-down positive, pitch nose-up positive, yaw as a NED heading (0 north, clockwise positive). `heading_deg` is in degrees.
- **Sticks:** roll right +, pitch forward +, yaw clockwise +, each −1..1; throttle 0..1. In altitude-hold modes 0.5 holds altitude.
- **goto yaw and ring headings:** compass degrees (0 north, clockwise).
- **Safety volume:** a box, 3 × 3 × 2 m by default (`safety_volume` in the fleet snapshot), centred horizontally on the aircraft's origin with its floor at the origin. The origin is the spawn point for a simulator and the first arming point for a real aircraft. `goto` targets outside it fail with `outside_safety_volume`; ring courses are scaled to fit it.

## 4. Authentication

| Caller | Header | WebSocket query parameter |
|---|---|---|
| Agent session | `X-Relay-Session: <token>` | `?session=<token>` |
| Operator (the Relay window) | `X-Relay-Operator: <token>` | `?operator=<token>` |

Read-only endpoints need no token. The API binds 127.0.0.1 only and answers only requests addressed to `127.0.0.1` or `localhost`. Writes have three permission levels:

| Level | Caller | Covers |
|---|---|---|
| Controller | The session that claimed the aircraft; the operator | Sticks, arm, mode, skills, plans, re-fly, courses, stop, device commands (motors, actuators, RC override, raw commands, reboot, calibration, termination), parameter writes |
| App operation | The operator; any session while the `agents_app_control` setting is on (the default) | Network scan, connect by address, remove aircraft, add, remove and reset simulators, stop-all, bridge retry and setup, alert acknowledgement, course edits, settings changes, interface actions (`POST /app/ui`) |
| Operator only | The Relay window only | Possess and release over REST, stick-direction and propeller attestations, granting or withdrawing `agents_app_control` |

With `agents_app_control` off, app operations from a session fail with 403 `app_control_disabled`; a session that tries to change the setting itself gets 403 `operator_required`. Every interface action a session runs shows a notice in the window and is logged as an `app_command` event.

**Rate limits** per session: control calls (sticks, arm, mode, skills) 60 per second, other calls 20 per second. Excess calls return 429 `rate_limited` with `Retry-After: 1`.

## 5. REST endpoints for agents

All paths are under `/api/v1`. Bodies are JSON.

| Method and path | Auth | Purpose |
|---|---|---|
| `GET /health` | – | `{ok, version, uptime_s}` |
| `GET /capabilities` | – | Frames, limits, skills and their parameters, mode names, confirm words |
| `GET /fleet` | – | Fleet snapshot: vehicles, sessions, alerts, safety volume |
| `GET /vehicles/{id}` | – | One vehicle, plus a `detail` object (home, safety origin, cell voltages, preflight items). `health` carries the flight diagnostics (§5) |
| `GET /vehicles/{id}/preflight` | – | Preflight check items |
| `GET /topology` | – | Station, vehicles, bridges, sessions, links and relative distances |
| `GET /events?after=&limit=&vehicle=&tail=` | – | Events with `seq > after`, oldest first; `tail=true` returns the newest `limit` |
| `GET /courses` | – | Preset and custom ring courses (scaled to the safety volume) |
| `POST /sessions` | – | `{name}` → `{session_id, name, token, lease_s}` |
| `POST /sessions/heartbeat` | session | Renew the lease |
| `DELETE /sessions` | session | Close the session and release its claims |
| `GET /sessions` | – | Open sessions (no tokens) and their recent calls |
| `POST /vehicles/{id}/claim` | session | Claim |
| `POST /vehicles/{id}/unclaim` | session | Release the claim |
| `POST /vehicles/{id}/sticks` | controller | `{roll, pitch, yaw, throttle}`; repeat at 10–50 Hz |
| `POST /vehicles/{id}/arm` | controller | `{arm: true}` (real aircraft: `{arm: true, confirm: "ARM"}`) or `{arm: false}` |
| `POST /vehicles/{id}/mode` | controller | `{name}`, for example `LOITER`, `ALT_HOLD`, `POSCTL` |
| `POST /vehicles/{id}/skills/{name}` | controller | `takeoff {alt}`, `land`, `hold {seconds?}`, `move {forward?, right?, up?}`, `yaw {deg}`, `rtl`, `goto {x, y, z, yaw?}` |
| `POST /vehicles/{id}/plan` | controller | `{steps, name?, confirm?}`: run a sequence of skills (below) |
| `POST /vehicles/{id}/plan/cancel` | controller | Cancel the running plan; an airborne aircraft holds where it is |
| `GET /history/sessions/{sid}/refly` | – | What a flight record can be flown again from: `plan`, `path`, `sticks` and `recommended` |
| `POST /vehicles/{id}/refly` | controller | `{session_id, mode?, speed?, confirm?}`: fly a record again (see below) |
| `POST /vehicles/{id}/course/start` | controller | `{course_id}` (default `cage-loop`) |
| `POST /vehicles/{id}/course/stop` | controller | Abort the course |
| `POST /vehicles/{id}/stop` | controller | Emergency stop |
| `POST /sims/{id}/assist` | controller or operator | `{on}`: hover assist of a simulated aircraft (below); `sim_only` for a real aircraft |

### Skills

A skill call returns at once with `{"skill": {"id", "name", "state": "running", "detail"}}`. The vehicle's `skill` field then reports the same `id` with `state` `running`, `done` or `failed`; events `skill_started`, `skill_finished` and `skill_failed` carry `data.skill_id`. Starting a new skill replaces the running one. The SDK waits on the id for you.

| Skill | Requires | Behaviour |
|---|---|---|
| `takeoff {alt}` | althold | Arms a simulator if needed, climbs to `alt` metres above the take-off point (0.2 m to the safety-volume height) and holds. With a position estimate it uses the autopilot's take-off (GUIDED / OFFBOARD); without one it climbs in ALT_HOLD / ALTCTL on the throttle stick and levels off on the barometer altitude. A real aircraft on the ground must be armed first, or the call must carry `confirm: "ARM"` and pass preflight. Already airborne: finishes immediately. |
| `land` | any | Lands in place; finishes when the aircraft is on the ground and disarmed. |
| `hold {seconds?}` | althold | Holds position (LOITER / POSCTL) or altitude (ALT_HOLD / ALTCTL). With `seconds`, reports `done` after that time and keeps holding. |
| `move {forward?, right?, up?}` | althold, airborne | Metres in the aircraft's body frame (negative values go back, left, down). With a position estimate: a closed-loop `goto` to the target. Without one: **open loop**, a timed tilt with a dead-reckoned distance estimate (about ±30 %), horizontal distance at most 2 m per step; `up` uses the barometer altitude. |
| `yaw {deg}` | althold, airborne | Turns by `deg` degrees, positive clockwise, on the attitude heading; finishes within 3°. |
| `rtl` | position | Returns to the launch point and lands. |
| `goto {x, y, z, yaw?}` | position | Flies to the target in the vehicle's position frame; finishes within 0.15 m. |
| `sticks {roll, pitch, yaw, throttle, seconds}` | manual, armed | Holds one stick position for `seconds` (0.05–10 s) in a manual mode, then centres the sticks. Lets a language model give short manual inputs. |
| `attitude {roll_deg, pitch_deg, yaw_rate_dps, thrust, seconds}` | manual, armed | Holds an attitude and collective thrust with `SET_ATTITUDE_TARGET` for `seconds` (ArduPilot switches to GUIDED_NOGPS, PX4 to OFFBOARD). |
| `velocity {vx, vy, vz, yaw_rate_dps?, seconds}` | position | Flies an ENU velocity (m/s) for `seconds`, then holds. |

While a skill runs or holds, Relay streams neutral sticks (throttle 0.5) as an RC keep-alive so the autopilot's RC-loss failsafe stays quiet; see `hardware.zh-CN.md` for the failsafe settings this relies on.

### Plans

A plan is an ordered list of up to 24 steps, each one skill, run one after another by Relay:

```json
POST /api/v1/vehicles/sim-1/plan
{"name": "bench", "steps": [
  {"action": "takeoff", "alt": 1.0},
  {"action": "hover", "seconds": 3},
  {"action": "move", "forward": 1},
  {"action": "move", "forward": -1},
  {"action": "yaw", "deg": 45},
  {"action": "land"}
]}
```

Actions: `takeoff {alt}` (default 1 m), `hover {seconds}` / `hold {seconds}` (default 3 s), `move {forward, right, up}`, `yaw {deg}`, `land`, `goto {x, y, z, yaw?}`, `rtl`, and `sticks`, `attitude` and `velocity` (parameters as in the table above). Every step is validated before the plan starts (`invalid_request` names the step and field; a step whose capability is missing fails with `capability_missing`). A plan that does not start with `takeoff` needs the aircraft in the air (`not_airborne`). On a real aircraft a plan that starts on the ground needs `confirm: "ARM"`.

The vehicle's `plan` field reports `{id, name, state, index, count, steps, results, detail}` with `state` `running`, `done`, `failed` or `cancelled`; events `plan_started`, `plan_step`, `plan_finished`, `plan_failed` and `plan_cancelled` mark progress. A step that fails, a new skill, sticks from the controller, an operator moving a stick or possessing the aircraft, and a stop all end the plan. `POST /plan/cancel` ends it on purpose (`no_plan` if none is running) and leaves an airborne aircraft holding.

`sdk/python/examples/bench_routine.py` flies the sequence above: `python3 sdk/python/examples/bench_routine.py --vehicle sim-1`; on a real aircraft add `--arm-real`.

### Re-fly (fly a past flight again)

Every flight records its plan, its track and its sticks (with their source: keyboard, gamepad, on-screen sticks or an agent). `GET /history/sessions/{sid}/refly` lists what a record offers; `POST /vehicles/{id}/refly` flies it again on any aircraft:

| `mode` | Behaviour |
|---|---|
| `plan` | The recorded plan, with the same steps and parameters |
| `path` | The recorded track as `goto` waypoints every 0.3 m, translated to the target's current position and flown as a plan; needs `position` |
| `sticks` | The sticks and mode changes from arming to disarming on the original time axis, scaled by `speed` (0.25–2.0); only for records flown in a manual mode |
| `auto` (default) | The first of `plan`, `path` and `sticks` the record offers |

`plan` and `path` return `{plan}`; `sticks` runs as the `replay` skill and returns `{skill}`. Follow them like any plan or skill; events `refly_started`, `refly_finished` and `refly_failed` mark the run. A missing record fails with `record_not_found`, a record without the requested source with `refly_unavailable`. A real aircraft that starts on the ground needs `confirm: "ARM"`; an operator takeover, stick input or a stop ends the re-fly.

### Device-level interface

The device-level interface reaches down to individual motors, output channels and MAVLink messages. Writes need the controller (claim first); calls that change the hardware state need a confirm word:

| Confirm word | For | When |
|---|---|---|
| `MOTOR` | Motor test, actuator commands that drive a motor output | Real aircraft |
| `ARM` / `FORCE` | Arm / force-arm (skips prearm checks) | Real aircraft |
| `REBOOT` | Reboot the autopilot | Real aircraft |
| `CALIBRATE` | Sensor calibration | Real aircraft |
| `TERMINATE` | Flight termination | Every aircraft, simulators included |

Motor tests, reboots and calibrations need the aircraft disarmed, otherwise 409 `must_be_disarmed`.

| Method and path | Auth | Purpose |
|---|---|---|
| `GET /vehicles/{id}/device` | – | Device overview: motor count, layout and per-output PWM, servo outputs, RC channels, frame type, sensor health, estimator status, vibration, home, parameter table counts, receive rate of every message |
| `GET /vehicles/{id}/messages/{name}` | – | The newest frame of one MAVLink message (fields, time, rate), for example `SERVO_OUTPUT_RAW` or `EKF_STATUS_REPORT` |
| `GET /vehicles/{id}/params/{name}` | – | One parameter; read by name from the autopilot (up to 2 s) when the table lacks it, else `param_not_found` |
| `POST /vehicles/{id}/params/read` | session | `{names}` (up to 32) read by name → `{values, missing}` |
| `POST /vehicles/{id}/params` | controller | `{name, value, confirm}`; `confirm` must equal the name |
| `GET /commands` | – | Raw command catalogue: MAV_CMD name and number, English and Chinese labels, parameter meaning and range, danger level, autopilots |
| `POST /vehicles/{id}/command` | controller | `{command, params[≤7], frame?, use_int?, confirm?, timeout_s?}`; catalogue commands only (`command_not_allowed`); returns the `COMMAND_ACK`. `DO_MOTOR_TEST` and `ACTUATOR_TEST` keep the motor-test limits (0.2–5 s, at most 30 % on a real aircraft) |
| `POST /vehicles/{id}/motors/test` | controller | `{motor: number or "all", throttle_pct, seconds (0.2–5), confirm}`; at most 30 % throttle on a real aircraft |
| `POST /vehicles/{id}/motors/stop` | controller | Stop a motor test now |
| `POST /vehicles/{id}/actuators/set` | controller | `{index 1–16, value −1..1 or pwm 800–2200, seconds, confirm?}`; `seconds` 0 holds until changed. Outputs 1 to the motor count are motors: `MOTOR`, a disarmed aircraft, `seconds` 0.2–5 and at most 30 % on a real aircraft |
| `POST /vehicles/{id}/rc` | controller | `{channels: {"1".."18": 1000–2000}}` or `{axes}`: one RC-override frame, expires after 0.8 s, replaces sticks |
| `POST /vehicles/{id}/message-interval` | controller | `{message, hz 0–50}`; 0 stops the stream |
| `POST /vehicles/{id}/request-message` | controller | `{message}`: ask the autopilot to send it once |
| `POST /vehicles/{id}/reboot` | controller | `{confirm}`: reboot the autopilot; the link comes back on its own |
| `POST /vehicles/{id}/calibrate` | controller | `{sensor: gyro | level | baro | accel_simple, confirm}` |
| `POST /vehicles/{id}/home` | controller | `{here: true}` or `{lat, lon, alt}` |
| `POST /vehicles/{id}/terminate` | controller | `{confirm: "TERMINATE"}`: motors stop at once and the aircraft is force-disarmed; an airborne aircraft falls |

Mode lists, arm, disarm and mode changes use the section 5 endpoints; `GUIDED_NOGPS` is available on ArduPilot.

### Application control

Application control lets an agent operate Relay itself: read and change the window, manage the fleet and the network, change settings. Interface actions run in the open Relay window, so the window must be running; the other app operations are carried out by the backend.

| Method and path | Auth | Purpose |
|---|---|---|
| `GET /app` | – | App overview: version, uptime, ports, scan state, counts of aircraft, sessions, controllers and alerts, whether a window is connected, `agents_app_control` |
| `GET /app/ui` | – | What the window shows: language, workspace, selected aircraft, view, inspector, dialogs, preferences, controllers and bindings, possession, window size, open record |
| `GET /app/gamepads` | – | Connected controllers and the aircraft they are bound to |
| `GET /app/actions` | – | Catalogue of interface actions and their arguments |
| `POST /app/ui` | app operation | `{action, args}`: run one interface action, waiting up to 5 s → `{ok, data}` |

Interface actions: `get_state`, `set_language {lang: en | zh}`, `set_workspace`, `select_vehicle {vehicle | null}`, `set_view`, `open_inspector`, `close_inspector`, `open_settings`, `open_connect`, `close_dialogs`, `set_pref`, `notify {text, level}`, `bind_gamepad`, `unbind_gamepad`, `possess`, `release`, `open_record`, `replay {play | pause | seek}`, `toggle_copilot`, `window {focus | minimize | maximize | restore | fullscreen}`, `screenshot {max_width}`. The `possess` action runs in the window and is the same as the operator possessing there: a person then flies the aircraft and agent claims are suspended.

Without a connected window the call fails with 503 `ui_unavailable`; no answer within 5 s gives 504 `ui_timeout`; an action the window refuses gives 409 `ui_action_failed`. Fleet, network, settings and alert operations use the existing paths in section 5 and the OpenAPI reference (`/discover`, `/vehicles`, `/sims`, `/stop-all`, `/network/retry`, `/bridges/{ip}`, `/alerts/{id}/ack`, `/courses/{id}`, `/settings`) at the "app operation" level of section 4.

### Flight health

Every vehicle carries `health`: rolling diagnostics over the last 5 s, shown in the inspector under Overview → Flight health. `state` is `ok`, `warn`, `bad` or `idle` (not armed); `items` lists `{key, level, value, unit, detail}` for `oscillation` (roll and pitch rate RMS, deg/s), `lean` (tilt held with centred sticks), `yaw_drift`, `alt_hold` (vertical speed spread in altitude hold), `hover_throttle`, `motors` (spread of mean motor outputs, saturation), `vibration` (peak, accelerometer clipping), `battery_sag` (per cell), `link` and `stick_stream` (stick updates from the Relay window while a person flies). Flight items are judged only after 1.5 s in the air; `level` is `na` until then. [`flight-tuning.zh-CN.md`](flight-tuning.zh-CN.md) explains each item and what to change.

### Sticks

Stick frames older than 0.8 s stop being sent, so the aircraft never flies on stale input. For continuous control, send at 10–50 Hz over REST or, better, over the WebSocket (`{"type": "sticks", "vehicle", "roll", "pitch", "yaw", "throttle"}`). Closing the WebSocket stops every stick stream it was feeding. MCP offers no continuous stick stream: a language model cannot close a 50 Hz loop; `relay_sticks_for` and the `sticks` skill hold one stick position for at most 10 s, then centre the sticks.

### Ring courses

`course/start` places the course at the vehicle's origin and returns it, including `rings` in the vehicle's frame: `c` (centre `[x, y, z]`), `yaw_deg` (compass heading of the ring normal) and `r` (radius). The clock starts at take-off. A ring counts when the aircraft crosses its plane inside the radius, in order. The vehicle's `course` field reports `next`, `total`, `splits`, `elapsed_s` and `best_s`; events `ring_passed` and `course_finished` mark progress. `course_sim.py` flies 0.35 m before and after each ring along its normal.

### Simulator hover assist

Every simulated aircraft has `hover_assist` (default: setting `sim_hover_assist`, on). On, it flies as before: ALT_HOLD holds height, LOITER holds position, GUIDED, RTL and LAND are autonomous. Off, it is a racing quad without barometer or position source: the attitude still self-levels, but the throttle is thrust (no height hold, no tilt or voltage compensation, the hover point rises as the battery sags), ground effect, motor lag, turbulence (setting `sim_turbulence`, 0–1) and propeller wake act, the aircraft reports no barometer and no position estimate (`capabilities.althold` and `position` false), and ALT_HOLD, LOITER, GUIDED, RTL and AUTO are refused with `Mode requires hover assist`. LAND stays as the failsafe and descends open loop. The switch is allowed armed and in flight: off moves an airborne aircraft to STABILIZE with a 0.3 s thrust ramp; on enters ALT_HOLD at the present height.

`POST /sims {count, autopilot, position, hover_assist}` sets it at creation; `POST /sims/{id}/assist {on}` switches it (the operator, the controlling session, or any session while nobody controls the aircraft and the operator allows app control). The snapshot carries `vehicle.sim = {hover_assist, turbulence}` (null on real aircraft); event `sim_assist_changed` reports a change. MCP: `app_sim_assist`; SDK: `sim_assist(id, on)` and `add_sims(count, autopilot, hover_assist)`.

## 6. WebSocket `/api/v1/stream`

Server → client:

```json
{"type": "hello", "version": "0.1.0", "operator": false, "session": "s-1a2b3c4d"}
{"type": "fleet", "data": { "...fleet snapshot..." }}
{"type": "event", "data": {"seq": 812, "kind": "ring_passed", "vehicle": "sim-1", "...": "..."}}
{"type": "error", "error": {"code": "not_claimed", "message_en": "...", "message_zh": "...", "detail": {}}, "ref": "sim-1"}
```

`fleet` arrives at 10 Hz and `event` as events happen. Client → server: `sticks` (above) and `{"type": "ping"}` (answered with `pong`). An invalid token closes the socket with code 4401; a disallowed browser origin closes it with 4403.

## 7. Events and errors

Each event is `{seq, t, kind, vehicle, session, text_en, text_zh, data}`. The kinds an agent usually watches:

| Kind | When |
|---|---|
| `possession_started` / `possession_released` | An operator took over or let go |
| `relay_handback` | Control returned to a suspended claim (`data.session_id`) |
| `claim_started` / `claim_released` | Claims changed |
| `agent_session_expired` | A lease ran out |
| `skill_started` / `skill_finished` / `skill_failed` | Skill progress, with `data.skill_id` |
| `plan_started` / `plan_step` / `plan_finished` / `plan_failed` / `plan_cancelled` | Plan progress, with `data.plan_id` |
| `armed` / `disarmed` / `mode_changed` | Autopilot state |
| `link_delayed` / `link_lost` / `link_restored` | Link quality; at `lost` Relay stops sticks and skills |
| `battery_warn` / `battery_critical` / `crashed` | Hazards |
| `course_started` / `ring_passed` / `course_finished` / `course_aborted` | Ring courses |
| `stop` / `stop_all` | Emergency stops |
| `refly_started` / `refly_finished` / `refly_failed` | Re-fly |
| `sim_assist_changed` | Hover assist of a simulated aircraft switched (`data.hover_assist`) |
| `device_command` / `motor_test` / `motor_test_stopped` / `actuator_set` / `rc_override` / `message_interval` / `home_set` / `rebooting` / `calibration_started` / `terminated` | Device-level operations |
| `app_command` | An interface action run by a session or the operator (`data.action`, `data.by`) |

The full list is in `web/src/api/schema.json` (`EventKind`). Errors share one body and keep their `code` stable across versions:

```json
{"error": {"code": "outside_safety_volume", "message_en": "The target is outside the safety volume.", "message_zh": "目标点超出安全区。", "detail": {"origin": [0, 0, 0], "volume": {"x": 3, "y": 3, "z": 2}}}}
```

| Status | Codes an agent meets |
|---|---|

## 8. MCP servers

Relay ships three stdio Model Context Protocol servers (JSON-RPC 2.0, standard library only; protocol versions 2024-11-05 to 2025-11-25). Connect any one of them or all three:

| Server | File | Tools | Scope |
|---|---|---|---|
| `anet-relay` | `mcp/anet_relay_mcp.py` | 20 `relay_*` | Flight: fleet, claims, arm, mode, skills, plans, timed sticks, re-fly, courses, stop |
| `anet-relay-device` | `mcp/anet_relay_device_mcp.py` | 29 `device_*` | Device level: overview, MAVLink messages, parameter reads and writes, raw commands, single-motor tests, actuators, RC override, message rates, reboot, calibration, home, attitude and velocity control, flight termination |
| `anet-relay-app` | `mcp/anet_relay_app_mcp.py` | 41 `app_*` | Application control: app and window state, controllers, language, workspace, selection, inspector, dialogs, screenshots, network scan, connecting and removing aircraft, simulators, settings, alerts, records and export, re-fly sources, possession, the Copilot window, stop-all |

Each server opens an agent session named by `--name` (defaults `mcp`, `mcp-device` and `mcp-app`) at start, renews its lease and closes it when the client disconnects. After a Relay restart it opens a new session on the next call; claims must then be made again. Claims belong to a session: fly an aircraft with the claim tool of the same server (`relay_claim` or `device_claim`). Arguments are checked before anything reaches Relay; missing or unknown ones come back as `invalid arguments`. Failures come back as tool results with `isError: true` and the error code, so a model can react (for example, wait on `possessed_by_human`).

The application server's tools work while `agents_app_control` is on; they need no operator token. `--operator-token` (or `RELAY_OPERATOR_TOKEN`) is only for calls made as the operator and is normally not needed.

## 10. Moving to a real aircraft

1. Set up the aircraft and its Wi-Fi bridge (`hardware.zh-CN.md`) and confirm it appears in the fleet as `real-<ip>`, for example `real-10-7-7-36`.
2. Complete the operator steps in the Relay window: verify stick directions without propellers, confirm propellers and the safety net, pass every blocking preflight item.
3. Replace the vehicle id in your code. Arming needs `confirm: "ARM"`. Position skills (`goto`, `rtl`, courses) need a local position source; without one, use `takeoff`, `hold`, `yaw`, `land` and open-loop `move` in altitude-hold modes, and expect the aircraft to drift slowly while it holds.
4. Keep an operator at the window. Possession and the stop button override any agent at any time.

## 11. Copilot (built-in agent)

The desktop app includes Copilot, a small agent built on [pi](https://github.com/earendil-works/pi) (`@earendil-works/pi-agent-core`). It runs in the app's main process and uses this API like any other agent: it opens a session named `copilot`, claims the aircraft it is asked to fly and appears in the Agents workspace and the relay timeline.

- **Floating window:** Copilot is a separate floating window that stays above other applications but is not modal: while it is shown you can keep clicking the Relay main window and any other application. Drag its title bar to place it anywhere on screen (including to the left of the main window) and its edges to resize it; position and size are remembered. The Copilot button in the top bar, Ctrl/Cmd + J or the window's own hide button shows or hides it. Each message carries the aircraft selected in the main window.
- **Setup:** Settings → Copilot: interface type (`openai-completions` for OpenAI-compatible endpoints, also `anthropic-messages` and `openai-responses`), base URL, model ID, API key, tool scope and window opacity (60–100 %). **Test connection** sends one short request. The key is encrypted with the operating system keychain (Electron `safeStorage`) in the app data directory and never returns to the interface; the endpoint receives only the conversation and tool results.
- **Tool scope:** `flight` (status, skills, plans, timed sticks, re-fly, stop), `flight+device` (adds the device-level tools) and `all` (the default; adds application control: language, workspace, selection, network scan, simulators, settings, controllers, records, window and screenshots). The tools map one to one onto the endpoints of section 5.
- **Safety:** every motion command and device write on a real aircraft (take-off, move, turn, hover, land, plans, re-fly, motor tests, actuators, reboot, calibration, termination and others) shows an approval card in the chat, and nothing is sent until the operator approves (120 s without an answer counts as declined); the floating window shows itself and flashes when an approval is waiting. The approval stands in for the confirm word; Copilot never fills one in on its own. Possession and stop work on Copilot exactly as on any other agent.
