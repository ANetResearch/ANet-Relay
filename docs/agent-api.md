# ANet Relay Agent API

English · [简体中文](agent-api.zh-CN.md)

ANet Relay exposes the fleet it flies to external programs: scripts, autonomous agents and language models. This guide covers the control model, the REST and WebSocket interface (flight, device and application levels), the Python SDK and the three MCP servers. The reference for every endpoint and model is generated by the running backend at `http://127.0.0.1:8765/docs` (OpenAPI at `/openapi.json`).

> **Safety.** Code written against simulators runs unchanged on real aircraft; only the vehicle id differs. Fly real aircraft only inside a netted area with a padded floor, with an operator at the Relay window who can take over or stop at any time.

## 1. Quick start (no hardware)

1. Start Relay. In the desktop app, click **Add sim** at the bottom of the fleet bar: a new simulator is an ANetDU7 (PX4, 2.5 kg, with a simulated gimbal pod); the small aircraft of 0.5 stay available through `frame.preset` ([ANetDU7](#anetdu7-and-speed-limited-flight-060)). From a source checkout you can run the backend alone: `.venv/bin/python -m relay --dev` (the operator token is printed once on stderr).
2. Fly a simulator with the Python SDK (standard library only, Python 3.10 or later):

```python
import sys
sys.path.insert(0, "sdk/python")            # or copy anet_relay_client.py next to your script
from anet_relay_client import RelayClient

with RelayClient() as relay:                # http://127.0.0.1:8765, or $RELAY_API
    relay.open_session("my-agent")          # the lease renews in the background
    relay.claim("sim-1")
    relay.takeoff("sim-1", alt=1.2)         # blocks until the skill finishes
    relay.goto("sim-1", 0.5, 0.5, 1.2)
    relay.land("sim-1")
```

> The high-level skills above need the agent flight level `full` (Settings → Safety, operator only). At the default level, `sticks`, an agent flies with sticks and onboard programs only: see [Agent flight level](#agent-flight-level) and the [program workflow](#program-workflow).

3. Or connect a language model through MCP (section 8): one server each for flight, device-level and application control.

The seven examples in `sdk/python/examples/` run against simulators:

| Example | What it does |
|---|---|
| `hover_sim.py` | Claim, arm, take off to 1.2 m, hover 8 s, land, release |
| `watch_handback.py` | Fly circles on sim-1; pause when a person possesses it; continue from the current position after `relay_handback` |
| `course_sim.py` | Fly the `cage-loop` ring course ring by ring with `goto` and print the result |
| `swarm_square.py` | Four simulators take off together, fly a synchronised square rotation and land |
| `bench_routine.py` | Take off, hover, forward 1 m, back 1 m, turn 45° and land as one plan |
| `device_tour.py` | Device overview, raw command catalogue, single-motor tests and an `attitude` hold |
| `du7_box_and_gimbal.py` | Fly the built-in `du7_box` plan on an ANetDU7 simulator, then point the gimbal, zoom, switch the lens, take a photo and print the capture record |

Each example accepts `--base` and `--name`. With `--operator-token` (or `$RELAY_OPERATOR_TOKEN`) the examples add missing simulators themselves; otherwise add them in the app (**Add sim**).

## 2. Control model

Relay is a relay of control between people and agents. Every aircraft has at most one controller at a time.

| Term | Meaning |
|---|---|
| **Session** | An agent identity. `POST /sessions {name}` returns a token and a lease (15 s). Any authenticated call renews the lease; `POST /sessions/heartbeat` renews it explicitly. An expired session loses its claims and its stick streams stop within 0.2 s. |
| **Claim** | A session's right to control an aircraft (`POST /vehicles/{id}/claim`). One claim per aircraft; claiming an aircraft held by another live session fails with `claimed_by_other`. |
| **Possession** | An operator flying the aircraft from the Relay window (keyboard, on-screen sticks or a gamepad). Possession always wins: it stops the agent's skill and sticks and **suspends** the claim. While suspended, every control call fails with `possessed_by_human` or `claim_suspended`. |
| **Hand-back** | When the operator releases, a live suspended claim becomes active again and Relay emits `relay_handback`. Relay sends nothing to the aircraft at that moment; the agent decides what happens next. |
| **Stop** | Emergency stop (`POST /vehicles/{id}/stop`): zero throttle for 50 ms, then a disarm request. It never changes who controls the aircraft. |

The `controller` field of each vehicle is `none`, `human` or `agent`.

An agent should therefore treat `possessed_by_human` and `claim_suspended` as "pause", watch the events for `relay_handback`, and re-read the vehicle state before continuing. `watch_handback.py` shows the pattern.

### Control levels and capabilities

| Level | Interface | Requires capability |
|---|---|---|
| 1 | `sticks` (roll, pitch, yaw, throttle) | `manual` (an autopilot heartbeat) |
| 2 | `arm`, `mode`, skills `takeoff`, `land`, `hold`, `move`, `yaw`; plans | `althold` for takeoff, hold, move and yaw |
| 3 | skills `goto`, `rtl`, ring courses; closed-loop `move` | `position` (a fresh local position estimate) |

Every vehicle reports `capabilities: {manual, althold, position}`. A missing capability fails with `capability_missing` or `no_position_estimate`. Simulators have all three. Real aircraft report `position` only with a local position source such as optical flow, motion capture or UWB.

### Agent flight level

Setting `agent_flight_level` (design 06 §5) decides what agent sessions may fly; only the operator changes it (Settings → Safety, or `PUT /settings` with the operator token). The operator in the window is never limited.

| Level | Agent sessions may |
|---|---|
| `sticks` (default) | Push sticks (WebSocket stream, `POST /vehicles/{id}/sticks`, the `sticks` skill), arm and disarm, switch to a manual mode (ArduPilot STABILIZE / ACRO, PX4 MANUAL / STABILIZED / ACRO; not DRIFT, which assists), switch a simulator's hover assist off (not on), fire, deploy and run onboard programs, and the safety actions: emergency stop and `land` (its events carry `safety`) |
| `full` | Everything in this guide, as in 0.3 |

At `sticks` the skills `takeoff`, `hold`, `move`, `yaw`, `goto`, `rtl`, `velocity` and `attitude`, plans that contain them, re-fly as a plan or a path, altitude, position and automatic modes, the flight commands of the device interface and RC overrides above channel 4 return 403 `sticks_only` with `detail.level = "sticks"` and `detail.action`. The flight MCP server lists only the tools that still work (29 of 38; it reads the setting on every `tools/list`), and Copilot drops the same tools and tells its model to write programs. Stable flight at this level is the job of an onboard program: the agent works at its own pace on the program, its parameters and its results, and the program closes the 50 Hz loop.

The gimbal pod is not a flight action: its actions (and the reads) work at both levels for the session that controls the aircraft, see [Gimbal pod](#gimbal-pod-060).

## 3. Frames and units

- **Position:** metres, East-North-Up: `x` east, `y` north, `z` up. All simulators share the frame `sim` (each spawns at a different grid point). Each real aircraft reports its own `local` frame, with its origin where the autopilot initialised its estimator.
- **Attitude:** radians; roll right-wing-down positive, pitch nose-up positive, yaw as a NED heading (0 north, clockwise positive). `heading_deg` is in degrees.
- **Sticks:** roll right +, pitch forward +, yaw clockwise +, each −1..1; throttle 0..1. In altitude-hold modes 0.5 holds altitude.
- **goto yaw:** degrees in the control frame ([Control frames](#control-frames-060); `flu`: 0 along east, counter-clockwise positive). **Ring headings** (`yaw_deg` of a ring) are compass degrees (0 north, clockwise).
- **Safety volume:** a box, 3 × 3 × 2 m by default (`safety_volume` in the fleet snapshot), centred horizontally on the aircraft's origin with its floor at the origin. The origin is the spawn point for a simulator and the first arming point for a real aircraft. `goto` targets outside it fail with `outside_safety_volume`; ring courses are scaled to fit it.

### Control frames (0.6.0)

The numbers of skills and plan steps that have a direction are read in a **control frame**. The default is `flu`, the convention of ROS and of the ANetDU7's onboard stack. A request names another one with `frame`; the operator changes the default with the setting `control_frame` (`flu` or `frd`, `PUT /settings`).

| Frame | Body x / y / z | Local x / y / z | Heading `yaw` | Positive yaw rate and `yaw` turn |
|---|---|---|---|---|
| `flu` (default) | forward / **left** / up | east / north / up (ENU: MAVROS `local_position`, ROS `map`) | 0° along +x (east), counter-clockwise positive | counter-clockwise |
| `frd` | forward / **right** / **down** | north / east / **down** (NED: PX4's local frame) | 0° north (compass), clockwise positive | clockwise |
| `relay` | forward / right / up | east / north / up | 0° north (compass), clockwise positive | clockwise |

`relay` is Relay's own set of axes and the meaning every release before 0.6 gave these parameters (see the echo rule below). The parameters read in the frame:

| Skill or step | Read in the frame | Not affected |
|---|---|---|
| `move` | `x, y, z`: body offsets in metres | the named directions `forward`, `right`, `left`, `up`, `down`: the same in every frame, so prefer them |
| `velocity` | `vx, vy, vz` (m/s) and `yaw_rate_dps`; `reference` `body` (the default, `local` in the `relay` frame) reads the three along the aircraft's axes, so the direction follows the nose; `local` reads them along the local axes | `seconds` |
| `goto` | `x, y, z`: local coordinates; `yaw`: heading in degrees | |
| `yaw` | `deg`: the turn, positive as in the last column | |
| `takeoff`, `land`, `hold`, `rtl`, `sticks`, `attitude` | | everything: `alt` is metres above the take-off point; `attitude` keeps roll right +, pitch nose-up + and `yaw_rate_dps` clockwise + |

`move` takes `x, y, z` or named directions, not both (`invalid_request`), and not `left` with `right` or `down` with `up`. The request body (or plan step) carries `frame` (`flu`, `frd` or `relay`; omitted: the setting) and, for `velocity` only, `reference` (`body` or `local`); anything else is `invalid_request`. A body-frame `velocity` is sent as `SET_POSITION_TARGET_LOCAL_NED` in `MAV_FRAME_BODY_NED` with the velocity and the yaw rate only, the frame MAVROS sends for `FRAME_BODY_NED`; the safety-volume look-ahead turns it to the local frame with the current heading.

**The echo rule.** The `skill_started` event carries `data.params` in the `relay` frame with `frame: "relay"` (a body velocity as forward, right, up with `reference: "body"`), whatever the setting or the request was. A recorded skill read back from the events therefore flies the same route under any setting, and the plans Relay builds itself (bench procedures, re-fly) use `relay`. What is not a command keeps its axes: `position`, `attitude`, `heading_deg`, the stick values and the ring course (`c` east-north-up, `yaw_deg` compass) are as before.

**`vehicle.nav`** reports the pose in the control frame of the setting, for agents that think in `flu` or `frd`: `{frame, position: [x, y, z] (local, metres; null without a local position), velocity: [vx, vy, vz] (local, m/s), body_velocity: [vx, vy, vz] (along the body axes, by heading only), yaw_deg, yaw_rate_dps}`. `GET /capabilities` carries `control_frame`, `control_frames` (the table above for `flu` and `frd`: `body` and `local` axis names, `yaw`, `yaw_rate`), `models` and `sim_frame_default`.

## 4. Authentication

| Caller | Header | WebSocket query parameter |
|---|---|---|
| Agent session | `X-Relay-Session: <token>` | `?session=<token>` |
| Operator (the Relay window) | `X-Relay-Operator: <token>` | `?operator=<token>` |

Read-only endpoints need no token. The API binds 127.0.0.1 only and answers only requests addressed to `127.0.0.1` or `localhost`. Writes have three permission levels:

| Level | Caller | Covers |
|---|---|---|
| Controller | The session that claimed the aircraft; the operator | Sticks, arm, mode, skills, plans, re-fly, courses, gimbal actions, stop, device commands (motors, actuators, RC override, raw commands, reboot, calibration, termination), parameter writes |
| App operation | The operator; any session while the `agents_app_control` setting is on (the default) | Network scan, connect by address, remove aircraft, add, remove and reset simulators, stop-all, bridge retry and setup, alert acknowledgement, course edits, settings changes, interface actions (`POST /app/ui`) |
| Operator only | The Relay window only | Possess and release over REST, stick-direction and propeller attestations, granting or withdrawing `agents_app_control`, setting a real aircraft's model, attaching and detaching a gimbal pod |

With `agents_app_control` off, app operations from a session fail with 403 `app_control_disabled`; a session that tries to change the setting itself gets 403 `operator_required`. Every interface action a session runs shows a notice in the window and is logged as an `app_command` event.

**Rate limits** per session: control calls (sticks, arm, mode, skills) 60 per second, other calls 20 per second. Excess calls return 429 `rate_limited` with `Retry-After: 1`.

### Skills

A skill call returns at once with `{"skill": {"id", "name", "state": "running", "detail"}}`. The vehicle's `skill` field then reports the same `id` with `state` `running`, `done` or `failed`; events `skill_started`, `skill_finished` and `skill_failed` carry `data.skill_id`. Starting a new skill replaces the running one. The SDK waits on the id for you.

| Skill | Requires | Behaviour |
|---|---|---|
| `takeoff {alt, speed?, settle_s?}` | althold | Arms a simulator if needed, climbs to `alt` metres above the take-off point (0.2 m to the safety-volume height) and holds. With a position estimate it uses the autopilot's take-off (GUIDED / OFFBOARD); without one it climbs in ALT_HOLD / ALTCTL on the throttle stick and levels off on the barometer altitude. With `speed`, or by default on an ANetDU7, PX4 with a position estimate arms in POSCTL, switches to OFFBOARD and climbs on speed-limited body velocity ([below](#anetdu7-and-speed-limited-flight-060)). A real aircraft on the ground must be armed first, or the call must carry `confirm: "ARM"` and pass preflight. Already airborne: finishes immediately. |
| `land` | any | Lands in place; finishes when the aircraft is on the ground and disarmed. |
| `hold {seconds?}` | althold | Holds position (LOITER / POSCTL) or altitude (ALT_HOLD / ALTCTL). With `seconds`, reports `done` after that time and keeps holding. |
| `move {forward?, right?, left?, up?, down? \| x?, y?, z?; frame?, speed?, settle_s?}` | althold, airborne | Metres in the aircraft's body frame. Name the direction (`forward`, `right`, `left`, `up`, `down`; negative values go the other way; the same in every frame) or give body offsets `x, y, z` in the control frame (`flu`: forward, left, up; `frd`: forward, right, down), not both. With a position estimate: a closed-loop `goto` to the target, on speed-limited body velocity when `speed` is given or on an ANetDU7. Without one: **open loop**, a timed tilt with a dead-reckoned distance estimate (about ±30 %), horizontal distance at most 2 m per step; `up` uses the barometer altitude. |
| `yaw {deg, frame?}` | althold, airborne | Turns by `deg` degrees on the attitude heading; positive is counter-clockwise in `flu` (the default) and clockwise in `frd` and `relay`; finishes within 3°. |
| `rtl` | position | Returns to the launch point and lands. |
| `goto {x, y, z, yaw?, frame?, speed?, settle_s?}` | position | Flies to the local point `x, y, z` of the vehicle's position frame, read in the control frame (`flu`: east, north, up; `frd`: north, east, down); the optional `yaw` is a heading in that frame (`flu`: 0 east, counter-clockwise; `frd`: compass). Finishes within 0.15 m; on speed-limited flight within 0.2 m held for `settle_s`, after turning to `yaw` first. |
| `sticks {roll, pitch, yaw, throttle, seconds}` | manual, armed | Holds one stick position for `seconds` (0.05–10 s) in a manual mode, then centres the sticks. Lets a language model give short manual inputs. |
| `attitude {roll_deg, pitch_deg, yaw_rate_dps, thrust, seconds}` | manual, armed | Holds an attitude and collective thrust with `SET_ATTITUDE_TARGET` for `seconds` (ArduPilot switches to GUIDED_NOGPS, PX4 to OFFBOARD). |
| `velocity {vx, vy, vz, yaw_rate_dps?, seconds, reference?, frame?}` | position | Flies a velocity (each −2..2 m/s) for `seconds`, then holds. `reference: "body"` (the default; `"local"` in the `relay` frame) reads the numbers along the aircraft's axes so the direction follows the nose (`flu`: forward, left, up; `frd`: forward, right, down); `"local"` along the local axes (`flu`: east, north, up; `frd`: north, east, down). `yaw_rate_dps` (−90..90) is counter-clockwise positive in `flu`, clockwise in `frd` and `relay`. |

While a skill runs or holds, Relay streams neutral sticks (throttle 0.5) as an RC keep-alive so the autopilot's RC-loss failsafe stays quiet; see `hardware.zh-CN.md` for the failsafe settings this relies on.

### Plans

A plan is an ordered list of up to 24 steps, each one skill, run one after another by Relay:

```json
POST /api/v1/vehicles/sim-1/plan
{"name": "bench", "steps": [
  {"action": "takeoff", "alt": 1.0},
  {"action": "hover", "seconds": 3},
  {"action": "move", "forward": 1},
  {"action": "move", "forward": -1},
  {"action": "yaw", "deg": 45},
  {"action": "land"}
]}
```

Actions: `takeoff {alt, speed?, settle_s?}` (default 1 m), `hover {seconds}` / `hold {seconds}` (default 3 s), `move {forward, right, left, up, down \| x, y, z; frame?, speed?, settle_s?}`, `yaw {deg, frame?}`, `land`, `goto {x, y, z, yaw?, frame?, speed?, settle_s?}`, `rtl`, and `sticks`, `attitude` and `velocity {…, reference?, frame?}` (parameters as in the table above). Each step reads its numbers in its own `frame`, omitted: the setting `control_frame`. Every step is validated before the plan starts (`invalid_request` names the step and field; a step whose capability is missing fails with `capability_missing`). A plan that does not start with `takeoff` needs the aircraft in the air (`not_airborne`). On a real aircraft a plan that starts on the ground needs `confirm: "ARM"`.

**Ready-made plans (0.6.0).** `POST /vehicles/{id}/plan {"builtin": "du7_box"}` flies a plan of `GET /plans/builtin` instead of `steps` (give one of the two, else `invalid_request`; the plan is named after it unless `name` says otherwise). `du7_box` is the route of the ANetDU7's onboard test node `u7_mavros_simple.py`: take off to 2 m, 1 m forward and back, 1 m left and back, land, every step at 0.5 m/s. Its directions are named, so it reads the same in every control frame; the 2 m take-off needs a safety volume at least 2 m high (the default). **0.6.1:** `du7_square10` is the outdoor 10 m square of the ANetDU7 (take off to 10 m, forward, left, back, right 10 m each, land; 2.5 m/s level, 0.5 m/s vertical); the safety volume must be at least 22 x 22 x 10.5 m. Speed-limited flight now caps the level speed at `speed` and a braking curve and the vertical speed at 0.5 m/s; a target counts `settle_s` after the aircraft first comes within 0.2 m, and a leg that never does ends at its approach limit (`skill.detail`: `approach limit reached … m from the target`). Plan steps take `forward` / `right` / `left` and move `x` / `y` up to 30 m.

The vehicle's `plan` field reports `{id, name, state, index, count, steps, results, detail, tuning}` with `state` `running`, `done`, `failed` or `cancelled`; events `plan_started`, `plan_step`, `plan_finished`, `plan_failed` and `plan_cancelled` mark progress, `plan_tuned` a change of the tuning. A step that fails, a new skill, sticks from the controller, an operator moving a stick or possessing the aircraft, and a stop all end the plan. `POST /plan/cancel` ends it on purpose (`no_plan` if none is running) and leaves an airborne aircraft holding.

**Throttle tuning (0.5.2).** Aircraft without a position estimate fly `takeoff`, `hover`, `move`, `yaw` and the PX4 `land` on the throttle stick in altitude hold. `tuning: {climb, hover}` sets those sticks: `climb` (0.55–1, default 0.72) lifts the aircraft off and climbs, `hover` (0.35–0.65, default 0.5) holds the height; the approach, descent and flare sticks keep their distance to `hover`, and `climb` must stay at least 0.05 above `hover`. Raise `climb` when the aircraft does not lift off and `hover` when it sinks while hovering. `PATCH /vehicles/{id}/plan/tuning` changes either value while the plan flies, also during the hold its last step or a cancel left behind; the step in flight takes it at once (`no_plan` without a plan). With a position estimate the autopilot flies take-off and holds itself and the tuning is not applied.

`sdk/python/examples/bench_routine.py` flies the sequence above: `python3 sdk/python/examples/bench_routine.py --vehicle sim-1`; on a real aircraft add `--arm-real`.

### Stick timelines (`.ars`, 0.5.3)

A timeline is four stick tracks (`throttle` 0..1; `pitch`, `roll`, `yaw` -1..1, forward, right and clockwise positive) on one time line, flown in a portable mode: `stabilize`, `althold` or `poshold` (STABILIZE / ALT_HOLD / LOITER on ArduPilot, STABILIZED / ALTCTL / POSCTL on PX4). The same file flies a simulator and a real aircraft. Files use the suffix `.ars` (ANet Relay Sequence):

```json
{"format": "ars", "version": 1, "name": "takeoff, hover, land", "mode": "althold", "duration_s": 19,
 "trim": {"roll": 0, "pitch": -0.04, "yaw": 0, "throttle": 0},
 "tracks": {"throttle": [{"t": 0, "v": 0.5}, {"t": 0.5, "v": 0.75, "label": "climb"}, {"t": 3, "v": 0.5, "label": "hover"},
                         {"t": 8, "v": 0.3, "label": "descend"}, {"t": 17, "v": 0}],
            "pitch": [{"t": 0, "v": 0}, {"t": 4, "v": -0.08, "ease": "ramp"}, {"t": 6, "v": 0}]},
 "end": "disarm"}
```

Each key starts a block that lasts until the next key: `hold` (default) keeps the stick at `v`, `ramp` moves it linearly to the next key's value. A missing track is centred (throttle 0.5 in the hold modes, 0 in stabilize). `trim` (roll, pitch, yaw ±0.3, throttle ±0.2) is added to every frame: cancel a forward drift with a negative pitch trim instead of editing the tracks. `end: "disarm"` disarms with zero throttle once the aircraft reports `landed: ground`; `hold` keeps holding (an `unknown` landed state counts as airborne). At most 600 s and 4000 keys per track; errors name the field, for example `sequence tracks.throttle[1].t: keys must be in time order`.

`POST /vehicles/{id}/sequence` switches the mode, arms on the ground (real aircraft: `confirm: "ARM"`), then plays; the vehicle's `skill` is `{name: "sequence", progress_s, duration_s, phase: mode | arm | play | end | hold}`. `PATCH` replaces the tracks (blocks not yet flown take effect at once; the mode cannot change) and / or the trim; `no_sequence` when none flies. `POST .../sequence/stop` stops without cutting anything. `POST .../sequence/record` records, at 20 Hz while armed, whatever sticks the aircraft receives (operator, plan, program, timeline) and returns them simplified to blocks; `GET /history/sessions/{sid}/sequence` does the same for a record. A simulator with hover assist off flies `stabilize` only; `poshold` needs `position`; at the `sticks` flight level sessions fly `stabilize` only. Events `sequence_started`, `sequence_edited`, `sequence_recording`.

**Arming needs stick input.** PX4 and ArduPilot arm a stick mode only while they see pilot input ("No manual control input", "Throttle below failsafe"); simulators now behave the same. When nothing feeds the aircraft, `POST /arm` first sends centred zero-throttle sticks (source `relay`) and waits 0.4 s; programs deployed with `arm` keep zero-throttle sticks while disarmed.

### Re-fly (fly a past flight again)

Every flight records its plan, its track and its sticks (with their source: keyboard, gamepad, on-screen sticks or an agent). `GET /history/sessions/{sid}/refly` lists what a record offers; `POST /vehicles/{id}/refly` flies it again on any aircraft:

| `mode` | Behaviour |
|---|---|
| `plan` | The recorded plan, with the same steps and parameters |
| `path` | The recorded track as `goto` waypoints every 0.3 m, translated to the target's current position and flown as a plan; needs `position` |
| `sticks` | The sticks and mode changes from arming to disarming on the original time axis, scaled by `speed` (0.25–2.0); only for records flown in a manual mode |
| `auto` (default) | The first of `plan`, `path` and `sticks` the record offers |

`plan` and `path` return `{plan}`; `sticks` runs as the `replay` skill and returns `{skill}`. Follow them like any plan or skill; events `refly_started`, `refly_finished` and `refly_failed` mark the run. A missing record fails with `record_not_found`, a record without the requested source with `refly_unavailable`. A real aircraft that starts on the ground needs `confirm: "ARM"`; an operator takeover, stick input or a stop ends the re-fly.

### Device-level interface

The device-level interface reaches down to individual motors, output channels and MAVLink messages. Writes need the controller (claim first); calls that change the hardware state need a confirm word:

| Confirm word | For | When |
|---|---|---|
| `MOTOR` | Motor test, actuator commands that drive a motor output | Real aircraft |
| `ARM` / `FORCE` | Arm / force-arm (skips prearm checks) | Real aircraft |
| `REBOOT` | Reboot the autopilot | Real aircraft |
| `CALIBRATE` | Sensor calibration | Real aircraft |
| `TERMINATE` | Flight termination | Every aircraft, simulators included |

Motor tests, reboots and calibrations need the aircraft disarmed, otherwise 409 `must_be_disarmed`.

Mode lists, arm, disarm and mode changes use the section 5 endpoints; `GUIDED_NOGPS` is available on ArduPilot.

### Application control

Application control lets an agent operate Relay itself: read and change the window, manage the fleet and the network, change settings. Interface actions run in the open Relay window, so the window must be running; the other app operations are carried out by the backend.

### Bench procedures

A bench procedure runs calibration and stability checks on one aircraft step by step and saves a report (S1 link and firmware, S2 battery at rest, S3 parameter baseline, S4 sensor calibration, S5 stick directions, S6 motor order and direction, S7 ground vibration, S8 propellers fitted, S9 hover test, S10 step response, S11 hover learning, S12 report). Procedures: `full_bench` (S1–S12), `preflight_quick` (S1, S2, S7, S9 for 10 s, S12), `motor_check` (S1, S6, S12), `vibration_check` (S1, S7, S9 for 20 s, S12) and `hover_tune` (S1, S8–S12). A procedure starts on a disarmed aircraft on the ground and needs control of it (claim, or the operator's possession).

| Method and path | Auth | Purpose |
|---|---|---|
| `GET /procedures` | – | Catalogue: `{procedures: [{id, title_en, title_zh, steps: [{id, title_en, title_zh, kind}], est_s}]}`; `kind` is `auto`, `operator`, `operator_device`, `device` or `flight` |
| `POST /vehicles/{id}/procedure` | controller | `{procedure, options: {hover_s 5–60, skip: [step ids], auto_answer}}`; `auto_answer` (simulators only) answers S6 from the servo outputs; S12 cannot be skipped → the run view |
| `GET /vehicles/{id}/procedure` | – | The current run, else the most recent saved one: `state` (`running`, `waiting`, `passed`, `warned`, `failed`, `aborted`), `step`, `index`, `total`, `paused`, `reason`, and per step `state`, `verdict`, `metrics` (value, unit, level, window `mean` / `peak`, `warn` / `bad` limits), `findings`, `suggestions`, `prompt`, `live` (recent points of the running step, 5 Hz) |
| `POST /vehicles/{id}/procedure/answer` | controller or operator | `{step, answer, confirm?}`: answer the waiting prompt; `answer` is one of `prompt.answers[].id` |
| `POST /vehicles/{id}/procedure/abort` | controller or operator | Abort: motor tests stop and an airborne aircraft lands |
| `GET /test-runs?vehicle=&limit=` | – | Saved reports, newest first, with verdict counts; `vehicle` matches the aircraft id or its address |
| `GET /test-runs/{run_id}` | – | One saved report with every step and the parameter baseline and changes |
| `GET /test-runs/{run_id}/export?fmt=md\|json` | – | The report as Markdown (bilingual tables, UTC times) or JSON, as a download |

A waiting step carries `prompt`: `{id, text_en, text_zh, detail_en, detail_zh, answers, confirm_word, operator_only, data}`. On a real aircraft `confirm_word` keeps the device rules: `MOTOR` before S6 and S7 spin motors (props off, at most 30 %, at most 5 s, disarmed; one word covers every motor of the step), `CALIBRATE` for each S4 calibration, `ARM` before S9 takes off, and the parameter name before S11 writes it (read back and checked). Prompts with `operator_only: true` (S5, S6, S8 and the S7 propeller check on a real aircraft) refuse sessions with 403 `operator_required`: a person must attest them at the Relay window. On a simulator an agent may answer every prompt.

The run is driven by the fleet loop, not by the caller: poll `GET .../procedure` (or watch the events) and answer when `state` is `waiting`. A run aborts on an emergency stop (the stop wins: no procedure landing follows), a lost link, a crash, a lost claim, or arming and disarming outside the flight steps. A session's run pauses while a person possesses the aircraft and resumes, from the start of the current step, once control returns and the aircraft is disarmed. Flight steps take off to 0.6 m, keep inside the safety volume and land by themselves; S10 flies short roll, pitch and yaw stick steps in altitude hold. On a simulator with hover assist off (no barometer or position source) S9 and S10 fail at once with the finding `hover_assist_off`, and a flight segment whose simulator loses hover assist in the air lands and fails. Suggested parameter changes (S10 rate gains, S11 hover throttle) are never written automatically: S11 asks for each one.

### Flight health

Every vehicle carries `health`: rolling diagnostics over the last 5 s, shown in the inspector under Overview → Flight health. `state` is `ok`, `warn`, `bad` or `idle` (not armed); `items` lists `{key, level, value, unit, detail}` for `oscillation` (roll and pitch rate RMS, deg/s), `lean` (tilt held with centred sticks), `yaw_drift`, `alt_hold` (vertical speed spread in altitude hold), `hover_throttle`, `motors` (spread of mean motor outputs, saturation), `vibration` (peak, accelerometer clipping), `battery_sag` (per cell), `link` and `stick_stream` (stick updates from the Relay window while a person flies). Flight items are judged only after 1.5 s in the air; `level` is `na` until then. [`flight-tuning.zh-CN.md`](flight-tuning.zh-CN.md) explains each item and what to change.

### Sticks

Stick frames older than 0.8 s stop being sent, so the aircraft never flies on stale input. For continuous control, send at 10–50 Hz over REST or, better, over the WebSocket (`{"type": "sticks", "vehicle", "roll", "pitch", "yaw", "throttle"}`). Closing the WebSocket stops every stick stream it was feeding. MCP offers no continuous stick stream: a language model cannot close a 50 Hz loop; `relay_sticks_for` and the `sticks` skill hold one stick position for at most 10 s, then centre the sticks.

### Ring courses

`course/start` places the course at the vehicle's origin and returns it, including `rings` in the vehicle's frame: `c` (centre `[x, y, z]`), `yaw_deg` (compass heading of the ring normal) and `r` (radius). The clock starts at take-off. A ring counts when the aircraft crosses its plane inside the radius, in order. The vehicle's `course` field reports `next`, `total`, `splits`, `elapsed_s` and `best_s`; events `ring_passed` and `course_finished` mark progress. `course_sim.py` flies 0.35 m before and after each ring along its normal. The ring numbers are in Relay's own axes (east-north-up, compass headings): fly them with `goto` and `frame: "relay"`, as that example does, or convert them to the control frame.

### Simulator hover assist

Every simulated aircraft has `hover_assist` (default: setting `sim_hover_assist`, on). On, it flies as before: ALT_HOLD holds height, LOITER holds position, GUIDED, RTL and LAND are autonomous. Off, it is a racing quad without barometer or position source: the attitude still self-levels, but the throttle is thrust (no height hold, no tilt or voltage compensation, the hover point rises as the battery sags), ground effect, motor lag, turbulence (setting `sim_turbulence`, 0–1) and propeller wake act, the aircraft reports no barometer and no position estimate (`capabilities.althold` and `position` false), and ALT_HOLD, LOITER, GUIDED, RTL and AUTO are refused with `Mode requires hover assist`. LAND stays as the failsafe and descends open loop. The switch is allowed armed and in flight: off moves an airborne aircraft to STABILIZE with a 0.3 s thrust ramp; on enters ALT_HOLD at the present height.

`POST /sims {count, autopilot, position, hover_assist, frame}` sets it at creation; `POST /sims/{id}/assist {on}` switches it (the operator, the controlling session, or any session while nobody controls the aircraft and the operator allows app control). The snapshot carries `vehicle.sim = {hover_assist, turbulence}` (null on real aircraft); event `sim_assist_changed` reports a change. MCP: `app_sim_assist`; SDK: `sim_assist(id, on)` and `add_sims(count, autopilot, hover_assist, frame)`.

### Simulator airframe defects

With hover assist off a simulated aircraft also flies with the assembly defects of a real one (design 06 §4). With hover assist on they wait, unless `with_assist` is set (0.5.3): then the CG offset, level error, motors, propeller, noise and weight act in altitude hold too, so a timeline can be tuned against an airframe that tilts and drifts like the real one.

| Value | Range | Effect |
|---|---|---|
| `mass_kg`, `payload_kg` | 0.08–0.30, 0–0.20 kg | Take-off weight: the hover throttle rises (0.12 kg hovers at 0.50, 0.16 kg at about 0.63); above the thrust limit (0.288 kg) the aircraft cannot lift |
| `cg_offset_cm` | [forward, right], ±3 cm | The angle loop leans toward the CG (2.5° per cm); airborne, its integrator removes 70 % of that with a 2 s time constant, the remaining 30 % is a steady tilt, so the aircraft drifts toward the CG. The integrator resets on the ground. A large offset saturates motors and the uncorrected remainder grows |
| `level_trim_deg` | [roll, pitch], ±5° | Level calibration error: with centred sticks the aircraft flies this much tilted while ATTITUDE reads level, so it drifts. The accelerometer (SCALED_IMU) still feels the push before drag builds up |
| `motor_gain` | 4 × ±0.08 | Efficiency deviation of motors 1–4 (ArduPilot X order): yaw drift (same 70 % / 2 s correction) and a small tilt disturbance; the motor outputs in SERVO_OUTPUT_RAW differ |
| `prop_damage`, `damaged_prop` | 0–1, motor 1–4 | That propeller loses up to 30 % thrust; VIBRATION rises by up to 50 m/s² at full throttle, accelerometer and gyro noise rise, the attitude jitters |
| `imu_noise` | 0–5 | Noise multiplier on ATTITUDE (0.08° roll and pitch, 0.15° yaw, 0.6°/s rates at 1) and SCALED_IMU (0.06 m/s²) |
| `arm_bias_deg` | 0–3° | A new random level error of up to this much on roll and pitch at every arming, added to `level_trim_deg` (a gyro bias that differs from flight to flight); repeatable from the seed and the arm count. `GET` reports this flight's error as `level_now_deg` |
| `with_assist` | boolean | The defects also act with hover assist on (voltage, ground effect and turbulence still need it off) |

Presets, generated deterministically from a seed (0 – 2^31−1): `ideal` (all zero: exactly the hover-assist-off model), `typical` (default: CG within 0.25 cm, level error within 0.4°, motors within 2 %, noise ×1), `rough` (CG 0.7–1.4 cm, level error 1–2°, motors within 8 %, one propeller 20–50 % damaged, 5–20 g payload, noise ×2: a naive hover drifts several metres in 20 s) and `custom` (explicit values).

`PUT /sims/{id}/airframe` takes `{preset}` (a fresh seed), `{preset, seed}`, `{seed}` (re-roll the current preset; a custom airframe keeps its values) or `{params: {...}}` (any subset, overlaid on the named preset or on the current values, which makes it `custom`). Allowed armed and in flight; the integrator starts again from zero. It returns, like `GET`, `{id, preset, seed, params, active, hover_throttle, limits}`; `hover_throttle` is the level hover throttle out of ground effect at full battery, null when the aircraft cannot lift. Who: the operator, the controlling session, or any session while nobody controls the aircraft and the operator allows app control; `sim_only` for a real aircraft, `invalid_request` names the bad field. `POST /sims` takes the same body as `airframe` (every new aircraft of the call gets it); without it each new simulator takes the setting `sim_airframe_default` (`ideal` | `typical` | `rough`, default `typical`) with a fresh random seed.

The snapshot carries only `vehicle.sim.airframe = {preset, seed}`: the values are never in the snapshot or in a program's observation; they show in flight. Event `sim_airframe_changed` (`data.preset`, `data.seed`, `data.by`). Simulators answer `SCALED_IMU` (board FRD specific force in mG, rates in mrad/s) when asked with `SET_MESSAGE_INTERVAL` or `REQUEST_MESSAGE`; it is in no stream group.

### Firmware twins (0.5.4)

A firmware twin is a simulator whose brain is the official firmware: the desktop (SITL) build of ArduCopter or PX4, the same version as a real aircraft and loaded with its parameters, runs as a child process of Relay and flies against Relay's physics in lockstep. To the rest of Relay it is a simulator (`sim-N`, `kind: "sim"`, `sim.engine: "sitl"`): claims, sticks, skills, plans, timelines, programs, the stage and the arena work unchanged, with the firmware's own control loop, arming checks and failsafes. The firmware only talks to Relay on loopback ports (127.0.0.1) and stops when the twin is removed, reset or Relay exits. Runtime packs ship with the installer (ArduCopter 4.7.2, 4.6.3, 4.5.7, 4.4.4, 4.3.8; PX4 1.17.0, 1.16.2, 1.15.4, 1.14.4; no PX4 on Windows); the format is in [Autopilot runtime packs](autopilot-packs.md).

| Method and path | Auth | Purpose |
|---|---|---|
| `GET /autopilots` | – | `{platform, bundled_dir, imported_dir, packs: [{id, family, vehicle, version, git, platform, size_bytes, license, source, built, origin: bundled \| imported, sha256, usable, problem, problem_zh, twins}]}` |
| `POST /autopilots/import` | operator | `{path, sha256?}`: import a pack tarball from a local path (checks the sha256 and the manifest) |
| `DELETE /autopilots/{id}` | operator | Delete an imported pack; bundled and running packs give `pack_unsupported` |
| `GET /vehicles/{id}/firmware` | – | `{identity: {family, vehicle, frame, version, type, git, board, board_id, identified}, params: {received, total, complete}, frame_problem, match: {recommended, match, warning_en, warning_zh, candidates: [{pack, version, git, match}]}}` |
| `GET /twins/profiles` | – | `{profiles: [{id, name, captured_at, updated_at, source, firmware, pack, match, frame, home, params_total, params_applied, params_excluded}]}` |
| `POST /twins/profiles` | app operation | `{from_vehicle, name?, frame?, profile?}`: capture a profile from a connected real aircraft whose parameters are read completely; `profile` recaptures into an existing one |
| `GET /twins/profiles/{pid}` | – | The profile with every parameter and `excluded: [{name, reason_en, reason_zh}]` (also the JSON export) |
| `PUT /twins/profiles/{pid}` | app operation | `{name?, frame?, pack?, home? \| null}`; the pack must be of the same firmware |
| `DELETE /twins/profiles/{pid}` | app operation | Delete a profile |
| `POST /sims` | app operation | `{count, engine: "sitl", profile?, pack?, frame?, home?}`: start twins; neither `profile` nor `pack` means the newest ArduPilot pack |
| `GET /sims/{id}/twin` | – | `{state: new \| booting \| running \| restarting \| exited \| failed \| stopped, pack, firmware, profile, instance, pid, home, frame, params: {applied, excluded, forced}, boot_s, restarts, exit, lockstep: {steps, stalls, frames, ms_per_step}}` |
| `PUT /sims/{id}/frame` | controller or operator | `{preset?, mass_kg?, wheelbase_m?, prop_in?, cells?, capacity_mah?}`: a new frame for a disarmed simulator on the ground (twin or fast simulator); `armed` otherwise |

- **Identification and matching.** Relay reads the firmware family, version, git hash and board from `AUTOPILOT_VERSION` and ranks the installed packs: `exact` (same version and git), `version`, `series` (same major and minor), `nearest`, `none`. Below `version` the answer carries a warning that the control loop and parameter meanings may differ. Any pack of the same firmware can be chosen; another firmware cannot. The snapshot gives every aircraft `firmware_info: {family, vehicle, version, type, git, board}` (null until `AUTOPILOT_VERSION` arrives).
- **Profiles.** Capturing needs a real aircraft (`real_only` otherwise) whose parameter table is read completely (`params_incomplete` with `detail.received/total`). Hardware-specific parameters (calibration offsets, device ids, serial ports, board and output wiring, PX4 `CAL_*`, `SYS_AUTOSTART`, ArduPilot `INS_*OFFS*`, `SERIAL*` and similar) stay out, each with an English and Chinese reason; gains, limits, failsafes and hover throttle go in. Without `frame` Relay guesses `large-450` for 4S or 2000 mAh and above, `small-250` otherwise.
- **Frames.** Presets `anet-du7` (the default of new fast simulators since 0.6.0), `micro-120` (the default of a twin without a profile), `small-250` and `large-450`, with mass, wheelbase, propeller, cells and capacity adjustable. A twin derives the motor thrust from the hover throttle in its parameters, so it hovers at the same throttle as the real aircraft.
- **Starting.** `POST /sims` returns once each firmware sends its first heartbeat; after 15 s the request fails with `twin_start_failed` (`detail.reason`, `detail.lines` with the last 40 lines of output, `detail.added`). `twin_limit` caps concurrent twins (setting `twin_limit`, default 8). With `engine: "relay"` (the default) `profile`, `pack` and `home` are refused; `frame` applies to both engines.
- **Reset and crashes.** `POST /sims/{id}/reset` restarts a twin's firmware with the same configuration in the background (event `twin_started` with `restart: true`, or `twin_start_failed`); it also recovers any crashed simulator. A twin that crashes keeps tumbling under the contact model like a fast simulator, and Relay tells the firmware with a `STATUSTEXT` from component 25.
- **Not on a twin.** The hover-assist switch and dogfights (`twin_unsupported`, `detail.operation`), `position: false` (`invalid_request`). Headless judging uses fast simulators only.

### Serial link and hardware in the loop (0.5.4)

| `GET /serial/ports` | – | `{available, reason, reason_zh, ports: [{device, name, description, manufacturer, vid, pid, serial_number, autopilot, kind, adapter, vehicle}]}`; `autopilot` marks known flight-controller USB interfaces (PX4/3DR, ArduPilot, CubePilot, Holybro, mRo, ST virtual COM) and `kind` is `autopilot`, `usb-serial` (a CP210x, FTDI or CH340 adapter, named in `adapter`) or `other`; `vehicle` is the aircraft already on the port. `available: false` means pyserial is missing. | `POST /vehicles` | app operation | `{serial: {device, baud?}}` instead of `{host, port?}` (not both) → `{id}`, for example `usb-ttyACM0`; `baud` is a rate or `"auto"` (115200, 57600, 921600 in turn, about 2 s each, until a heartbeat arrives; USB CDC autopilots ignore it). The snapshot carries `transport: "udp" \| "serial" \| "sim"` and `serial: {device, baud, open, error, reopened, usb} \| null`. A port that fails is closed and reopened about once a second; a USB board that comes back under another name is found again by its USB serial number. `DELETE /vehicles/{id}` closes the port |
| `GET /vehicles/{id}/hitl` | – | `{id, available, reason, reason_zh, cause, state, steps, backup, changed, mismatches, volatile, error, run, pending_restore}`; `cause` says why `start` is not possible (`sim`, `unidentified`, `ardupilot`, `other_firmware`, `not_serial`, `busy`, `pending`, `link`, `armed`, `possession`); `volatile` lists self-changing parameters (flight-time counters, the flight UUID) that the verification does not compare; `error` is `{code, step, message, message_zh}` |
| `POST /vehicles/{id}/hitl` | operator, or app operation | `{action: start \| stop, confirm?: "HITL"}` → the same status object |

Hardware in the loop (HITL) runs a real PX4 flight controller against Relay's physics: Relay backs up every parameter to `hitl-backups/<vehicle>-<time>.json` in the data directory, sets `SYS_HITL = 1` and the HIL quadcopter X airframe (`SYS_AUTOSTART 1001`), reboots the board, then feeds it `HIL_SENSOR` at 250 Hz and `HIL_GPS` at 10 Hz and moves the physics with its `HIL_ACTUATOR_CONTROLS`. The firmware keeps the motors locked. The aircraft shows as "Hardware in the loop" with an engine label such as "Hardware in the loop PX4 1.16.2", and the snapshot carries `hitl: {state, engine: "hitl", label_en, label_zh, firmware: {family, version}, pending_restore, pose} \| null`; while it runs, the aircraft's `position` (frame `local`), `attitude` and `rates` show the physics the board is fed. Only `SYS_HITL` and `SYS_AUTOSTART` are changed; `SYS_AUTOCONFIG` is left alone because it would reset every parameter. Integers are compared by value and reals by their stored bytes. `stop` (or a disconnect, or the next connection after Relay exits) writes back every changed parameter, reboots, reads all parameters again and compares them with the backup; differences are reported as `mismatches` (`hitl_restore_mismatch`) and the backup file stays.

- `state`: `idle`, `backing_up`, `writing`, `rebooting`, `running`, `restoring`, `verifying`, `restored`, `failed`. `steps`: `confirm`, `backup`, `write`, `reboot`, `run`, `restore`, `verify`, each `pending`, `active`, `done`, `failed` or `skipped` with an English and Chinese `detail`. `run`: `{sensor_hz, gps_hz, actuator_frames, steps, since}` while running. Any failed step goes to the restore.
- `start` needs `confirm: "HITL"` (the propellers are removed), a PX4 aircraft on a serial link, disarmed, and the operator's possession; an agent session may run it only while app control is on. Without the word, `confirm_required` (400, `detail.expected: "HITL"`); otherwise `hitl_unavailable` (409) with `detail.reason`, `detail.reason_zh` and `detail.cause`. A restore owed by an earlier session (Relay quit while it ran) runs on its own the next time the board connects over serial, and only while it is disarmed; `stop` also runs it at once. ArduPilot removed HIL from its firmware; for an ArduPilot aircraft use a firmware twin. A Wi-Fi telemetry link cannot carry the sensor stream, so HITL needs USB.
- Status: the PX4 protocol (encoding, backup, restore and verification) is tested against a simulated serial port; the whole flow on a real board is verified once the larger PX4 aircraft is available.

### ANetDU7 and speed-limited flight (0.6.0)

The ANetDU7 is the main aircraft of 0.6: a 2.5 kg quadcopter (500 mm wheelbase, 684 × 684 × 211 mm with its guard frame, 4S 5300 mAh, about 10 minutes) with a CUAV X7+ flight controller running PX4, an onboard computer and a gimbal pod. `vehicle.model` is `anet-du7` or `micro` (the small aircraft of 0.5). The aircraft is told apart by its model, not by its autopilot.

| Where | Rule |
|---|---|
| New simulator | `POST /sims` without `frame` adds ANetDU7s: the setting `sim_frame_default` (default `anet-du7`; `micro-120`, `small-250`, `large-450` choose the small aircraft). A request's `frame.preset` overrides it. An `anet-du7` simulator without an `autopilot` named flies the PX4 flavour, the small presets ArduPilot. Firmware twins (`engine: "sitl"`) keep their profile's frame, else `micro-120` |
| Simulator model | `anet-du7` when its physics preset is `anet-du7`, else `micro`; it follows the frame (`PUT /sims/{id}/frame`). An `anet-du7` simulator carries a simulated gimbal pod |
| Real aircraft | The setting `real_model_default` (default `anet-du7`), until the operator sets it: `POST /vehicles/{id}/model {"model": "anet-du7" \| "micro"}` (operator only, remembered per airframe, event `model_changed`) |
| Dogfights, challenges, built-in programs | Always `micro-120`, unchanged |
| `GET /capabilities` → `models` | `anet-du7`: span 0.684 m, height 0.211 m, wheelbase 0.5 m, 2.5 kg, gimbal; `micro`: 0.166 m, 0.045 m, 0.25 m, 0.12 kg, no gimbal. The stage draws them at real size |

**Speed-limited tracking.** `takeoff`, `move` and `goto` take `speed` (m/s, 0.1–5) and `settle_s` (0–10, default 2). With `speed`, or by default on an `anet-du7` aircraft with a position estimate (`speed` 0.5), they fly the way the onboard test node does instead of sending position setpoints. Every 50 ms the velocity is 0.8 × the position error, capped at `speed`, with its change limited to 0.5 m/s²; it is turned to the body frame and sent as a body velocity with a zero yaw rate (the nose is not corrected, and a `goto` with `yaw` turns on the spot first). The step is done when the aircraft has stayed within 0.2 m horizontally and vertically for `settle_s`. A PX4 take-off sends zero velocities in POSCTL for 2 s, arms, switches to OFFBOARD and climbs from the arming point; ArduPilot keeps `NAV_TAKEOFF` and flies `move` and `goto` in GUIDED. Without a position estimate `move` stays open loop. `speed` or `settle_s` on any other skill is `invalid_request`, and `settle_s` without `speed` on an aircraft that is not an `anet-du7`. The skill times out after `40 + 2·alt/speed` s (take-off) or `30 + 2·distance/speed` s.

Monitors, as in the test node: a tilt over 20°, a position jump over 0.25 m + 1.5 m/s × dt (an estimator reset), position telemetry older than 1 s (the test node allows 0.3 s onboard; Relay sees the position over the radio link), or a speed over `speed` + 0.5 m/s for 1 s ask the autopilot to land once and fail the skill with the reason in `skill.detail`. When the mode is changed from outside (the pilot's radio), the skill fails and no more setpoints are sent.

### Gimbal pod (0.6.0)

`vehicle.gimbal` is the aircraft's gimbal pod, `null` on an aircraft without one. Every ANetDU7 simulator carries a simulated pod (`kind: "sim"`, same clock as the physics, deterministic). A real ANetDU7's pod (`kind: "dyt"`, the DYT pod; protocol notes in `vehicles/anet-du7/docs/gimbal-dyt.zh-CN.md`) is attached by the operator over TCP (port 2000 of the onboard network) or a serial port. One set of actions drives both. Reads are anonymous; `POST /vehicles/{id}/gimbal` is for the operator or the session that controls the aircraft (possession or a live claim), **at every agent flight level**, and needs no confirm word. Attaching and detaching are the operator's.

Angles are the pod's own frame angles and do **not** follow `control_frame`: `yaw_deg` right positive, `pitch_deg` up positive (looking straight down is −90), `roll_deg` right positive.

| `kind`, `link`, `address` | `sim` or `dyt`; `ok`, `connecting` or `lost`; `"10.0.0.5:2000"` or the serial device, null for the simulated pod |

| `mode` | `follow`, `lock`, `rate`, `angle`, `track`, `scan` or `off` (motors off) |

| `zoom`, `zoom_range`, `digital_zoom`, `fov_deg` | Magnification of the current lens, its range, the digital-zoom switch, current `[horizontal, vertical]` field of view (estimated for a DYT pod) |

### Onboard programs

An onboard program (design 06 §2) is a restricted Python program with `PARAMS`, `init(ctx)` and `step(obs, ctx) -> Sticks` that Relay runs in an isolated program host at 50 Hz on the aircraft's stick path. It sees only what the aircraft measures (`obs`: attitude, rates, accelerations, barometric height, optional position, battery, motor output, arena state, contacts) and outputs the four sticks and the trigger. [`programs-guide.md`](programs-guide.md) is the compact reference for writing one (the same text is in Copilot's instructions and in the MCP tool `program_guide`); [`programs.md`](programs.md) is the full documentation.

| Method and path | Who | Purpose |
|---|---|---|
| `GET /programs` | – | Built-in examples (`hover_trim`, `liftoff`, `patrol`, `hunter_easy`, `hunter_medium`, `hunter_hard`, `rammer`, `figure8_evader`; read-only) and stored programs |
| `POST /programs` | session or operator | `{name, source?, description?, params?, tests?, note?, copy_of?}` → `{program, validation}` |
| `GET /programs/{pid}` · `GET /programs/{pid}/revisions` | – | One program (`source`, `params`, `tests`, `rev`); the last 50 revisions, newest first, with author and note |
| `PUT /programs/{pid}` | session or operator | `{source}` or `{patch: [{start, end, text}]}` (1-based, inclusive, numbered against the current revision; `end = start - 1` inserts), plus `name`, `description`, `params`, `tests`, `note`: a new revision; returns `{program, validation}` |
| `DELETE /programs/{pid}` | session or operator | Delete a stored program |
| `POST /programs/{pid}/validate` | session or operator | `{source?}`: language check only, `{ok, errors: [{line, col, code, message_en, message_zh}], params, param_ranges}` |
| `POST /programs/{pid}/test` | session or operator | `{rev?, source?, tests?, seed?}`: run the unit tests, `{results, passed, total}` |
| `POST /vehicles/{id}/program` | controller or operator | `{program, rev?, params?, mode: pilot \| copilot, sensors?, arena?, seed?, airframe?, team?, arm?, confirm?}`: deploy; `arm: true` sets STABILIZE (PX4 STABILIZED) and arms once the program is in place, so it flies at once (`confirm: "ARM"` on a real aircraft; checked before anything changes), and the answer's `arm {ok, code?, reason?}` says whether the autopilot armed: a refusal leaves the program in place, waiting on the ground. A deployment that armed the aircraft disarms it when it stops on the ground; `team` (1–16 characters) is the aircraft's team in every contact list and fills the program's `team` parameter when it declares one; the program holds the sticks as `PROGRAM · <name>` |
| `POST /vehicles/{id}/program/stop` · `.../resume` | controller or operator | Stop; resume a paused program |
| `PATCH /vehicles/{id}/program/params` | controller or operator | `{name: value}`: live parameters, type and range from `PARAMS` and `PARAM_RANGES` |
| `GET /vehicles/{id}/program/log?after=&limit=` | – | Log ring (500 lines): `{lines: [{seq, t, level, text}], last_seq}` |
| `POST /vehicles/{id}/program/allow` | operator | `{allow, confirm: "PROGRAM"}`: allow programs on a real aircraft (reset when the link drops) |

The snapshot carries `vehicle.program` (`{id, name, rev, state, status: running | paused | faulted | stopped, fps, faults, last_error, mode, ...}`) and `programs_allowed`. Rules that always hold: a person who possesses the aircraft pauses a `pilot` program and releasing never resumes it; emergency stop, link loss and a crash stop it; the claim ending, the session's own sticks and any skill or plan supersede it; stale sticks time out after 0.8 s as before. Real aircraft accept a program only while the operator's **Allow programs on this aircraft** switch is on and preflight passes, and their `fire` output is ignored. `ctx.disarm()` asks for a disarm after the frame and is honoured only while the landed state says the aircraft is on the ground (refused once with a log line otherwise). A new revision deployed while a program flies takes over in the air without a gap.

### Challenges and duels

Onboard programs (design 06 §2) are judged like exercises on a practice site: a **challenge** is a fixed scenario with a scoring rule, a **duel** sets 2–8 programs against each other in the arena. Both run in a **headless evaluator**: a separate worker process that builds an isolated fleet (no sockets, nothing on disk, an injected clock) and steps the same simulated autopilot, airframe defects, stick path, arena rules and program engine as live flight, as fast as the machine allows (about 13× real time with one aircraft, 5–6× with two and 3.5–4× with four). Hover assist is always off. The same scenario, seeds and program revisions always give the same result. At most two jobs run at once; the rest wait in a queue of 16.

| Method and path | Auth | Purpose |
|---|---|---|
| `GET /challenges` | – | `{challenges: [{id, kind, name_en, name_zh, goal_en, goal_zh, scene_en, scene_zh, duration_s, visible_seeds, hidden_seeds, opponent, best, attempts}]}` |
| `GET /challenges/{id}` | – | Adds `scoring_*`, `sensors`, `hover_assist`, `info` (corners, rings and other public parameters) and the last 20 submissions in `history` |
| `POST /challenges/{id}/submit` | session or operator | `{program, rev?, params?, visible_only?}` → `{job}`; every visible and hidden seed, or only the visible ones with `visible_only` (not counted as best) |
| `POST /duels` | session or operator | `{programs: [id or {program, rev?, params?}, …2–8], rounds? (1–20, default 3), seed? (default 1), scenario?: {duration_s (10–180), arena, airframe (ideal / typical / rough), sensors, turbulence}}` → `{job}` |
| `GET /jobs`, `GET /jobs/{id}` | – | `{job: {id, kind, state (queued / running / done / failed / cancelled), progress, queue_position, programs, result, error}}` |
| `DELETE /jobs/{id}` | session or operator | Cancel a queued or running job (its worker is stopped) |
| `GET /ladder` | – | `{ladder: [{rank, program, name, rating, games, wins, draws, losses}], duels}` (Elo, start 1200) |
| `GET /traces/{id}` | – | A replay trace (below) |

| Challenge | Scenario | Passes when |
|---|---|---|
| `liftoff` | Payload: hover throttle about 0.62; barometer, no position | Off the ground within 5 s, then 3 s without a break at 1.0 ± 0.2 m |
| `hover` | CG forward of the middle and a level error; barometer, no position | From 6 to 26 s: drift ≤ 0.8 m and height 1.0 ± 0.25 m (judged on the truth) |
| `heading` | Unequal motor efficiencies (yaw drift) | From 5 to 20 s: heading within 10° of the spawn heading, at least 0.4 m up |
| `square` | UWB-like position (10 Hz, σ 5 cm) | The four corners of `info.corners` (radius 0.4 m) in order within 40 s; faster scores higher |
| `rings` | The `cage-loop` ring course, UWB-like position | Every ring in order within 60 s; timed |
| `pursuit` | A scripted target circles the centre (3 m, 0.5 m/s, 1.2 m up); contacts and UWB-like position | Within 2 m of the target for at least half of the 60 s; the score is that share |
| `duel_easy` / `duel_medium` / `duel_hard` | One against one with `hunter_easy` / `hunter_medium` / `hunter_hard` (arena radius 8 m, ceiling 4 m) | A win: the opponent shot down, crashed or out of the arena while you still fly; time up scores by hit points left |
| `ram_easy` | A target hovers on the spawn ring (`judge_hover_target`); guns are off; contacts and UWB-like position | The target crashes from a collision with you within 60 s; faster and harder impacts score higher, a near miss scores by the closest approach |

Scores are 0–100. A submission runs every seed, passes when every seed passes and scores their mean; `result = {score, passed, metrics, seeds: [{seed (null when hidden), hidden, score, passed, metrics, trace_id}], trace_id, best, speed}`. Hidden seeds fly other airframes and leave no trace. Each challenge keeps its best full submission and the last 50 in `<data_dir>/programs/results.json`.

A duel round puts one aircraft per program on a ring of spawn points around the arena centre (shuffled and with airframes seeded by `seed + round − 1`), all facing the centre. An aircraft is out when it is shot down, crashes or leaves the arena box; the round ends when one is left (after one second) or the time is up. Placement: still flying first, then survival time, hit points, hits. The last aircraft flying wins the round; otherwise it is a draw. The ladder (`<data_dir>/programs/ladder.json`) moves by pairwise Elo over each round's placements (K = 32, split over the other entrants). `result = {rounds: [{round, seed, winner, draw, duration_s, aircraft: [{id, program, alive, hp, hits, hits_taken, survived_s, reason, place}], trace_id}], standings, ladder: [{program, rating, delta}], speed}`. Event `judge_finished` (`data.job`, `data.state`, `data.score`, `data.passed`) when a job ends.

A **trace** (`GET /traces/{id}`, gzip on disk, the newest 300 kept) replays every aircraft of one seed or round at 10 Hz: `{id, job, version: 1, kind, challenge?, round?, scenario, seed, hz, duration_s, fields: ["x", "y", "z", "roll", "pitch", "yaw", "throttle", "hp", "flags"], arena, course, markers, t: [...], aircraft: [{id, label, program, rev, name, role, team, spawn, frames: [[…one row per t…]], states: [[t, state]]}], shots: [{id, shooter, t0, p, v}], events: [{t, kind, vehicle, …}], result}`. Positions are world ENU metres with the arena centre at the origin (the snapshot's frame), attitude in radians (yaw is the compass heading 0..2π), `flags` bits 1 armed, 2 airborne, 4 shot down, 8 crashed, 16 out. A shot leaves `p` at `t0` with velocity `v` and follows the arena ballistics (`web/src/arena/ballistics.ts`). Events: `hit`, `down`, `crash`, `out`, `liftoff`, `corner`, `ring`, `course_finished`, `program_faulted`, `program_stopped`. The full contract is in the `relay.judge` module docstring and in `Trace` of `web/src/api/schema.json`.

The SDK, the MCP tools and Copilot report `judge_unavailable` when they talk to a Relay older than 0.4.0, which has none of these routes.

### Program workflow

The loop an agent goes through, here with the SDK at the default `sticks` level (the MCP tools and Copilot's tools have the same names: `program_create`, `program_update`, `program_validate`, `program_test`, `challenge_submit`, `program_deploy`, `program_params`, ...):

```python
with RelayClient() as relay:
    relay.open_session("my-agent")
    # 1. write: start from the built-in hover_trim
    pid = relay.program_create("My hover", copy_of="hover_trim", note="start")["program"]["id"]
    relay.program_update(pid, patch=[{"start": 14, "end": 14, "text": '    "target_alt": 1.2,'}], note="higher")
    # 2. validate: language rules, line and column of each problem
    assert relay.program_validate(pid)["ok"]
    # 3. test: the unit tests in the program host
    print(relay.program_test(pid))
    # 4. submit to a challenge (headless, hidden seeds)
    print(relay.challenge_submit("hover", pid)["result"])
    # 5. deploy on a simulator with physical flight and a rough airframe
    relay.claim("sim-1")
    relay.sim_assist("sim-1", False)
    relay.mode("sim-1", "STABILIZE")
    relay.arm("sim-1")
    relay.program_deploy("sim-1", pid, airframe={"preset": "rough", "seed": 7})
    # 6. watch and tune live; stop when done
    print(relay.program_status("sim-1"), relay.program_log("sim-1")["lines"][-5:])
    relay.program_params("sim-1", ki=0.2)
    relay.program_stop("sim-1")
```

Every edit is a new revision with its author (`operator` or the session name) and note, so a result can always be traced to the code that produced it. Tune parameters live first; change code when the structure is wrong; resubmit to the challenge, whose hidden seeds catch a program tuned to one airframe.

### LAN arena

The arena (05 §7) lets Relay terminals on the same broadcast domain see each other's simulated aircraft, fire virtual rounds at them, and score hits. It is joined from the window (top bar **Arena**, setting `peer_enabled`) and uses one UDP socket of its own (setting `peer_port`, default 47114, multicast `239.255.71.14` with TTL 1 plus subnet broadcast). Nothing received from the network reaches a control path: no stick, arm, claim, parameter, skill, plan or device call is ever driven by a peer packet. **Real aircraft never join the arena and are never affected by virtual rounds**: only simulators are shared, can fire and can be hit.

| Method and path | Who | Purpose |
|---|---|---|
| `GET /arena` | – | `{enabled, instance, seat, callsign, error, peers: [{id, callsign, seat, rtt_ms, stale, score, vehicles}], shots, local: {ammo, hp, reloading, reload, down, max_ammo, max_hp, score}}`; positions are already in this terminal's local ENU frame |
| `POST /vehicles/{id}/fire` | controller | `{seconds}` (0–3, default 1; 0 releases): hold the trigger of an armed, airborne simulator; 8 rounds/s, 24 per magazine, 1.5 s reload; `arena_off` outside the arena, `arena_down` after a shoot-down, `sim_only` for a real aircraft |

A round deals 20 damage (five bring a simulator down) and pushes the airframe; a shot-down simulator stops its motors, falls, disarms on the ground and returns to its seat's spawn point after 5 s (setting `arena_auto_respawn`) or on a reset. Hits are not safety events: they raise no alert. Settings: `peer_enabled`, `peer_port`, `peer_callsign` (≤ 16 characters; empty uses the computer name), `arena_auto_respawn`. SDK: `arena()`, `fire(id, seconds)`.

### Dogfights, matches and the leaderboard

A **dogfight** (07 §3) is a timed fight of 2–8 simulators in the arena, each flown by an onboard program at the `sticks` level: **gunners** fire, **rammers** fly into their targets and never fire. One call sets it up: Relay takes free simulators (and adds the rest), places them on a ring of spawn points 3 m inside the arena edge facing the centre, sets hover assist and the airframe, opens a session named `dogfight` that claims them, deploys the program of each role (`hunter_medium` and `rammer` by default), arms them, and the programs take off themselves. The operator can possess any aircraft at any time: its program pauses (state `human`) and resumes on release. With `respawn` a shot-down or crashed aircraft (state `down`) is back at its spawn point after 5 s and flies again. At the end (time up, `DELETE`, or every aircraft failed) the programs stop, airborne aircraft land, a simulator still up after 20 s or sitting on the ground without the landing detector firing is disarmed with the checks skipped, the claims are released and the final standings stay on the leaderboard. On the LAN the dogfight joins the running match or starts one on every version 2 terminal; with the arena off it runs in **practice mode** (the arena rules without a socket; nothing is sent) and leaves it at the end. **Real aircraft are refused** (`dogfight_real_aircraft`); they never take part in matches, collisions or scenarios.

| Method and path | Who | Purpose |
|---|---|---|
| `POST /scenarios/dogfight` | app control (session with `agents_app_control`, or the operator) | `{aircraft (2–12, default 6; more than 8 → dogfight_no_aircraft), teams ("ffa" / 2 / 3), roles: {gunner, rammer} (sum = aircraft; default 2 gunners : 1 rammer), programs: {gunner, rammer}, arena: {radius (3–30, default 8), ceiling (2–10, default 4)}, airframe (ideal / typical / rough), hover_assist (default false), duration_s (30–1800, default 180), respawn (default true), seed, vehicles, entrants}` → the dogfight view. `entrants` (2–8) sets each aircraft on its own and replaces `aircraft`, `roles` and `teams`: `{role: gunner \| rammer \| pilot (never fires), program (required for pilot; default per role), team (≤ 16 characters; default its own id), position: none \| uwb \| gps (default none), params, label}`; `dogfight_running` while one runs |
| `GET /scenarios/dogfight` | – | `{running, phase (idle / booting / arming / deploying / running / ending / done), started_at, ends_at, config, aircraft: [{vid, role, program, team, position, label, state (booting / arming / deploying / flying / human / down / stopped / failed)}], match, by, reason (time / stopped / error), error}` |
| `DELETE /scenarios/dogfight` | app control | End it early; `dogfight_not_running` without one |
| `POST /arena/match` | app control | `{duration_s}` (30–1800, default 180): a match here and on every version 2 peer; `arena_off`, `match_running` |
| `DELETE /arena/match` | app control | End the running match everywhere (`ended: true`); without one, reset the statistics (`ended: false`) |
| `GET /arena/leaderboard?by=` | – | `{by, match, rows: [{key, aircraft, callsign, local, controller: {kind (program / agent / human / none), name}, downs, hits, shots, accuracy, rams, deaths, crashes, damage, alive, alive_s, best_alive_s}]}`, sorted by `downs` (default), `survival`, `accuracy` or `rams` |

**Statistics.** Every simulator in the arena has a line: downs (a round of its brought another aircraft down), hits, shots, rams (a collision it caused crashed the other aircraft), deaths (shot down), crashes (collision or ground), damage dealt, the current survival time and the longest one. A match (`{id, origin, started_at, duration_s, running, ended_at, reason (time / stopped / conflict)}`) resets the lines at its start and freezes them at its end; the arena snapshot carries `match` and `board_rev`. Rows of a LAN peer come from its own statistics (it counts what it saw); a Relay 0.4 peer's rows have null statistics.

**Wire protocol 2.** Relay 0.5 speaks version 2 of the arena protocol and stays compatible with 0.4: every packet 0.4 knows is still sent with version byte 1, byte for byte; version 2 is used only for `COLLIDE`, `MATCH` and, about once a second, a `STATE` that carries the statistics block (a 0.4 terminal drops those as malformed and keeps the other states). A peer is version 2 from its first valid version 2 packet; matches and collisions only involve version 2 peers. `MATCH` starts or ends a match on every terminal (the earliest start wins a conflict; it is repeated every 2 s while running). **LAN collisions**: each terminal sweeps its own aircraft against the peers' (as last reported, extrapolated at most 0.15 s); on a contact it applies the response to its own aircraft and sends `COLLIDE` to the owner of the other one. The owner applies it only after checking it again: at most 0.3 s old (clock difference and half the round trip), the two aircraft within 0.6 m of each other at the contact time on its own view, at most 4 per second per peer aircraft, once per pair within 0.5 s; it answers with a reply (never answered again) so the sender learns about a crash it caused. A rejected `COLLIDE` changes nothing. Event `collision` (`data.a`, `data.b`, `data.b_label`, `data.point`, `data.v_rel`, `data.crashed`, `data.kind`, `data.remote`).

SDK: `dogfight_start(...)`, `dogfight_stop()`, `dogfight_status()`, `leaderboard(by)`, `match_start(duration_s)`, `match_end()`. MCP (application server) and Copilot: `dogfight_start`, `dogfight_stop`, `dogfight_status`, `leaderboard`. A request such as "a six-aircraft free-for-all, four gunners and two rammers" maps to `dogfight_start {aircraft: 6, teams: "ffa", roles: {gunner: 4, rammer: 2}}`. "Three aircraft: A flies a figure eight and evades with global position, one rams A, one shoots A" maps to `dogfight_start {entrants: [{role: "pilot", program: "figure8_evader", team: "A", position: "gps", label: "A"}, {role: "rammer", team: "B"}, {role: "gunner", team: "B"}]}`: the attackers see A only as a contact, A gets position and velocity.

## 6. WebSocket `/api/v1/stream`

Server → client:

```json
{"type": "hello", "version": "0.1.0", "operator": false, "session": "s-1a2b3c4d"}
{"type": "fleet", "data": { "...fleet snapshot..." }}
{"type": "event", "data": {"seq": 812, "kind": "ring_passed", "vehicle": "sim-1", "...": "..."}}
{"type": "error", "error": {"code": "not_claimed", "message_en": "...", "message_zh": "...", "detail": {}}, "ref": "sim-1"}
```

`fleet` arrives at 10 Hz, `arena` (the `GET /arena` view) at 20 Hz, and `event` as events happen. Client → server: `sticks` (above), `{"type": "fire", "vehicle", "on"}` (the controller's trigger, refreshed every 100 ms while held; 300 ms without a refresh releases it) and `{"type": "ping"}` (answered with `pong`). An invalid token closes the socket with code 4401; a disallowed browser origin closes it with 4403.

## 8. MCP servers

Relay ships three stdio Model Context Protocol servers (JSON-RPC 2.0, standard library only; protocol versions 2024-11-05 to 2025-11-25). Connect any one of them or all three:

| Server | File | Tools | Scope |
|---|---|---|---|
| `anet-relay` | `mcp/anet_relay_mcp.py` | 38 `relay_*` (29 at the `sticks` level) | Flight: fleet (with `model`, `nav` and a gimbal summary), claims, arm, mode, skills (`relay_takeoff`, `relay_move`, `relay_yaw`, `relay_goto` take `frame`, `speed`, `settle_s` where they apply), plans (`steps` or `builtin`; `relay_plans_builtin` lists the ready-made ones) and their throttle tuning, stick timelines (`relay_timeline_*`, also in `acro`), timed sticks, re-fly, courses, stop; the gimbal pod: `relay_gimbal_status`, `relay_gimbal_control {action, ...}`, `relay_gimbal_captures` (available at every level for the aircraft you claimed); firmware twins: `relay_autopilots_list`, `relay_firmware_identify`, `relay_twin_profiles_list`, `relay_twin_profile_get`, `relay_twin_profile_capture`, `relay_twin_start`, `relay_twin_status`, `relay_sim_frame` (available at every level: a twin is a simulator) |
| `anet-relay-device` | `mcp/anet_relay_device_mcp.py` | 36 `device_*` | Device level: overview, MAVLink messages, parameter reads and writes, raw commands, single-motor tests, actuators, RC override, message rates, reboot, calibration, home, attitude and velocity control (`device_velocity` takes `frame` and `reference`), flight termination, bench procedures and their reports |
| `anet-relay-app` | `mcp/anet_relay_app_mcp.py` | 45 `app_*`, `relay_serial_ports`, `relay_hitl`, 19 program tools and 4 dogfight tools | Application control: app and window state, controllers, language, workspace, selection, inspector, dialogs, screenshots, network scan, connecting (`app_connect_address {host}` or `{serial: {device, baud}}`) and removing aircraft, serial ports, simulators (`app_sims_add {engine: relay \| sitl, profile, pack, frame, home}`: without `frame` an ANetDU7, `frame.preset` `micro-120`, `small-250` or `large-450` for the small aircraft; `app_sim_reset` also recovers crashed simulators and restarts a twin's firmware), PX4 hardware in the loop (`relay_hitl {vehicle, action: status \| start \| stop, confirm: "HITL"}`), settings (`app_settings_set {settings: {control_frame, sim_frame_default, ...}}`), alerts, records and export, re-fly sources, possession, the Copilot window, stop-all; operator actions `app_set_model`, `app_gimbal_attach`, `app_gimbal_detach`; onboard programs: `program_guide`, `program_*`, `challenge_list`, `challenge_submit`, `job_status`, `duel_run`, `ladder`, `airframe_set`; dogfights: `dogfight_start`, `dogfight_stop`, `dogfight_status`, `leaderboard` |

Each server opens an agent session named by `--name` (defaults `mcp`, `mcp-device` and `mcp-app`) at start, renews its lease and closes it when the client disconnects. After a Relay restart it opens a new session on the next call; claims must then be made again. Claims belong to a session: fly an aircraft with the claim tool of the same server (`relay_claim` or `device_claim`). Arguments are checked before anything reaches Relay; missing or unknown ones come back as `invalid arguments`. Failures come back as tool results with `isError: true` and the error code, so a model can react (for example, wait on `possessed_by_human`).

The application server's tools work while `agents_app_control` is on; they need no operator token. `--operator-token` (or `RELAY_OPERATOR_TOKEN`) is only for calls made as the operator and is normally not needed; `app_set_model`, `app_gimbal_attach` and `app_gimbal_detach` are operator actions and fail with `operator_required` without it.

The application server's program tools that act on an aircraft (`program_deploy`, `program_stop`, `program_resume`, `program_params`) claim it for that server's session; if the flight server's session holds the claim, release it there first (`relay_release_claim`). `program_deploy` with `arm: true` switches to a manual mode and arms before it deploys (a real aircraft also needs `confirm: "ARM"`).

## 10. Moving to a real aircraft

1. Set up the aircraft and its Wi-Fi bridge (`hardware.zh-CN.md`) and confirm it appears in the fleet as `real-<ip>`, for example `real-10-7-7-36`.
2. Complete the operator steps in the Relay window: verify stick directions without propellers, confirm propellers and the safety net, pass every blocking preflight item.
3. Replace the vehicle id in your code. Arming needs `confirm: "ARM"`. Position skills (`goto`, `rtl`, courses) need a local position source; without one, use `takeoff`, `hold`, `yaw`, `land` and open-loop `move` in altitude-hold modes, and expect the aircraft to drift slowly while it holds.
4. Keep an operator at the window. Possession and the stop button override any agent at any time.
5. An ANetDU7 (`hardware.zh-CN.md`, section ANetDU7, and `vehicles/anet-du7/README.md`): its MAVROS must send MAVLink to Relay's UDP 14550 with a unique `MAV_SYS_ID`, and its pod is attached with `gimbal_attach` (TCP port 2000). Real aircraft are shown as `anet-du7` until the operator sets `micro`; take-off, `move` and `goto` then fly on speed-limited body velocity (0.5 m/s) whenever a position estimate exists, with the monitors above. Fly the first flight with `du7_box` and an operator at the window.

## 11. Copilot (built-in agent)

The desktop app includes Copilot, a small agent built on [pi](https://github.com/earendil-works/pi) (`@earendil-works/pi-agent-core`). It runs in the app's main process and uses this API like any other agent: it opens a session named `copilot`, claims the aircraft it is asked to fly and appears in the Agents workspace and the relay timeline.

- **Floating window:** Copilot is a separate floating window that stays above other applications but is not modal: while it is shown you can keep clicking the Relay main window and any other application. Drag its title bar to place it anywhere on screen (including to the left of the main window) and its edges to resize it; position and size are remembered. The Copilot button in the top bar, Ctrl/Cmd + J or the window's own hide button shows or hides it. Each message carries the aircraft selected in the main window.
- **Setup:** Settings → Copilot: interface type (`openai-completions` for OpenAI-compatible endpoints, also `anthropic-messages` and `openai-responses`), base URL, model ID, API key, tool scope and window opacity (60–100 %). **Test connection** sends one short request. The key is stored in the app data directory (`copilot-secrets.json`, AES-256-GCM with a random per-installation key in `copilot-secrets.key`, both readable only by your user account) and never returns to the interface; the endpoint receives only the conversation and tool results. **Store keys in the system keychain** (off by default) keeps the key in the macOS Keychain, Windows credential encryption or the Linux Secret Service instead; only then does Relay call Electron `safeStorage`. Relay never reads or needs your system login password: a keychain dialog comes from the operating system and appears only when you choose the keychain. A key saved by 0.3 or earlier stays in the keychain untouched until you either enter it again or choose **Keep using keychain** in the Copilot window.
- **Thinking and output limit:** **Thinking** (`auto`, the default, leaves it to the endpoint; `off`, `low` and `high` set it for reasoning models such as DeepSeek V4) and **Max output tokens** (1024–131072, default 16384, per model call with the thinking included). Reasoning models think by default and their thinking shares the output limit: a call that runs out reports `length` and the chat says so instead of staying silent.
- **Copy and formatting (0.5.2):** replies render Markdown: headings, nested and task lists, tables with column alignment (scrollable when wide), fenced code, quotes and links (opened in the system browser). The transcript is selectable; right-click offers Copy, Paste and Select All in every Relay window, each reply has a copy button for its Markdown, tables copy as tab-separated values and code blocks copy their text.
- **Run trace:** every message gets a small red pixel aircraft under it that flies while Copilot works and names the phase (waiting for the model, thinking with the characters so far, writing, preparing a tool call with the argument characters, a tool running, waiting for approval) and the time; while the chip is out of view the same chip sits above the input. A click opens the trace of the run: each model call with its time, input / output / thinking tokens and stop reason, expandable to the full thinking, the reply and the tool calls it asked for, and each tool with its arguments and full result.
- **Tool scope:** `flight` (status, skills, plans, timed sticks, re-fly, stop), `flight+device` (adds the device-level tools) and `all` (the default; adds application control: language, workspace, selection, network scan, simulators, settings, controllers, records, window and screenshots). The tools map one to one onto the endpoints of section 5.
- **Safety:** every motion command and device write on a real aircraft (take-off, move, turn, hover, land, plans, re-fly, motor tests, actuators, reboot, calibration, termination and others) shows an approval card in the chat, and nothing is sent until the operator approves (120 s without an answer counts as declined); the floating window shows itself and flashes when an approval is waiting. The approval stands in for the confirm word; Copilot never fills one in on its own. Possession and stop work on Copilot exactly as on any other agent.
- **Allow all (0.5.2):** the approval card's **Allow all** button (or Settings → Copilot → **Allow all**) approves that command and every later one on real aircraft without asking. Each command is still recorded in the chat as approved automatically, and a red **Allow all** badge in the Copilot title bar stays visible while it is on; a click on the badge turns it off. Relay's own gates do not change: preflight, the operator's **Allow programs on this aircraft** switch, possession and emergency stop. Hardware in the loop is the exception: `relay_hitl` start and stop always ask (0.5.4).
- **Firmware twins and hardware in the loop (0.5.4):** in every scope and at both flight levels Copilot has the twin tools (`relay_autopilots_list`, `relay_firmware_identify`, `relay_twin_profiles_list`, `relay_twin_profile_get`, `relay_twin_profile_capture`, `relay_twin_start`, `relay_twin_status`, `relay_sim_frame`); a twin is a simulator, so they need no approval. In scope `all` it adds `relay_serial_ports`, `app_connect {serial}` and `relay_hitl`. `relay_hitl` start and stop always show an approval card, on any aircraft and also while **Allow all** is on: the card has no **Allow all** button and asks the operator to confirm the propellers are removed. `relay_hitl` status needs no approval.
- **ANetDU7, control frames and the gimbal (0.6.0):** the flight tools take `frame`, `speed` and `settle_s` where they apply (`relay_takeoff`, `relay_move` with the named directions or `x, y, z`, `relay_yaw`, the steps of `relay_plan` including `goto`, `device_velocity` with `reference`), `relay_plan {builtin: "du7_box"}` and `relay_plans_builtin` fly the ready-made plan (full flight level), and `relay_gimbal_status`, `relay_gimbal_control` and `relay_gimbal_captures` drive the pod in every tool scope and at both flight levels (Copilot claims the aircraft first; a pod moves without an approval card, also on a real aircraft). Its instructions teach `flu` as the default, the sign of each axis and when to pass `frame`; `app_add_sim` takes the aircraft preset. Operator-only calls (setting a real aircraft's model, attaching a pod) are not Copilot tools.
- **Programs and the flight level:** Copilot reads `agent_flight_level` before every message. At `sticks` (the default) it has no take-off, move, turn, hover, plan or re-fly tools and its instructions say that high-level flight is unavailable and that stable flight needs a program; at `full` it has them again. In every tool scope it has the program tools (`program_list`, `program_get`, `program_create`, `program_update`, `program_validate`, `program_test`, `program_deploy`, `program_stop`, `program_resume`, `program_params`, `program_status`, `program_log`, `challenge_list`, `challenge_submit`, `job_status`, `duel_run`, `ladder`, `airframe_set`) plus `relay_arm`, `relay_disarm` and `relay_mode`, and its instructions end with [`programs-guide.md`](programs-guide.md). Writing and editing programs needs no approval; deploying or resuming a program on a real aircraft, arming it and changing its mode wait for the operator's approval like every other motion. `program_deploy {arm: true}` arms the aircraft with the deployment, and at `full` the plan tools take `tuning` and `relay_plan_tune` retunes a flying sequence, so Copilot can run the whole write, test, fly and tune loop.

## 12. Upgrading from 0.5

The behaviour changes of 0.6.0, and how to get the old behaviour back:

1. **The default simulator is the ANetDU7.** `POST /sims` (and **Add sim**, SDK `add_sims`, MCP `app_sims_add`, Copilot `app_add_sim`) without a frame adds ANetDU7s: 2.5 kg, PX4 flavour, a simulated gimbal pod, take-off, `move` and `goto` on speed-limited body velocity at 0.5 m/s. For the small ArduPilot aircraft of 0.5 pass `frame: {preset: "micro-120"}` (`add_sims(frame="micro-120")`) or set `sim_frame_default` to `micro-120`. Dogfights, judged challenges and built-in programs always use `micro-120` and are unchanged.
2. **Unnamed axes are read in `flu` by default.** `move {x, y, z}` (new), `velocity {vx, vy, vz, yaw_rate_dps}`, `goto {x, y, z, yaw}` and `yaw {deg}` use the control frame: left and counter-clockwise are positive (before: `yaw {deg}` and `goto yaw` were clockwise and compass; `velocity` was ENU, now it follows the nose unless `reference: "local"`). Named directions (`forward`, `right`, `up`, new `left`, `down`) and `goto x, y, z` in `flu` mean what they meant (east, north, up). To get the old meaning of a call exactly, send `frame: "relay"` (SDK `frame="relay"`, MCP and Copilot `frame`); `control_frame` offers only `flu` and `frd`, so `relay` stays a per-request choice. `skill_started` params are always echoed in `relay` axes.
3. **Real aircraft are `anet-du7` by default** (`real_model_default`), so take-off, `move` and `goto` with a position estimate fly on speed-limited body velocity at 0.5 m/s with the tracking monitors. Set the aircraft to `micro` (`POST /vehicles/{id}/model`, `set_model`, `app_set_model`) or `real_model_default` to `micro` to keep the autopilot's own setpoints, or pass `speed` explicitly.
4. **SDK:** `add_sims` no longer sends `autopilot="ardupilot"` (the server picks PX4 for an ANetDU7); `takeoff`, `move` and `goto` compute their wait timeout from `speed`; `plan(steps=None, ..., builtin=)`; `__version__` is 0.6.0.
5. **New:** the gimbal pod (`vehicle.gimbal`, `/vehicles/{id}/gimbal`, gimbal tools in the flight and app servers, `gimbal_*` SDK methods, Copilot tools), `vehicle.model` and `vehicle.nav`, `GET /plans/builtin` and `du7_box`, events `gimbal_*` and `model_changed`, errors `gimbal_*`, settings `control_frame`, `sim_frame_default`, `real_model_default`, `vehicle_models`. The flight MCP server has 38 tools (29 at the `sticks` level, was 34 and 26) and the app server 70 (was 67).
