# ANet Relay Agent API

English · [简体中文](agent-api.zh-CN.md)

ANet Relay exposes the fleet it flies to external programs: scripts, autonomous agents and language models. This guide covers the control model, the REST and WebSocket interface (flight, device and application levels), the Python SDK and the three MCP servers. The reference for every endpoint and model is generated by the running backend at `http://127.0.0.1:8765/docs` (OpenAPI at `/openapi.json`).

> **Safety.** Code written against simulators runs unchanged on real aircraft; only the vehicle id differs. Fly real aircraft only inside a netted area with a padded floor, with an operator at the Relay window who can take over or stop at any time.

## 1. Quick start (no hardware)

1. Start Relay. In the desktop app, click **Add sim** at the bottom of the fleet bar. From a source checkout you can run the backend alone: `.venv/bin/python -m relay --dev` (the operator token is printed once on stderr).
2. Fly a simulator with the Python SDK (standard library only, Python 3.10 or later):

```python
import sys
sys.path.insert(0, "sdk/python")            # or copy anet_relay_client.py next to your script
from anet_relay_client import RelayClient

with RelayClient() as relay:                # http://127.0.0.1:8765, or $RELAY_API
    relay.open_session("my-agent")          # the lease renews in the background
    relay.claim("sim-1")
    relay.takeoff("sim-1", alt=1.2)         # blocks until the skill finishes
    relay.goto("sim-1", 0.5, 0.5, 1.2)
    relay.land("sim-1")
```

> The high-level skills above need the agent flight level `full` (Settings → Safety, operator only). At the default level, `sticks`, an agent flies with sticks and onboard programs only: see [Agent flight level](#agent-flight-level) and the [program workflow](#program-workflow).

3. Or connect a language model through MCP (section 8): one server each for flight, device-level and application control.

The six examples in `sdk/python/examples/` run against simulators:

| Example | What it does |
|---|---|
| `hover_sim.py` | Claim, arm, take off to 1.2 m, hover 8 s, land, release |
| `watch_handback.py` | Fly circles on sim-1; pause when a person possesses it; continue from the current position after `relay_handback` |
| `course_sim.py` | Fly the `cage-loop` ring course ring by ring with `goto` and print the result |
| `swarm_square.py` | Four simulators take off together, fly a synchronised square rotation and land |
| `bench_routine.py` | Take off, hover, forward 1 m, back 1 m, turn 45° and land as one plan |
| `device_tour.py` | Device overview, raw command catalogue, single-motor tests and an `attitude` hold |

Each example accepts `--base` and `--name`. With `--operator-token` (or `$RELAY_OPERATOR_TOKEN`) the examples add missing simulators themselves; otherwise add them in the app (**Add sim**).

## 2. Control model

Relay is a relay of control between people and agents. Every aircraft has at most one controller at a time.

| Term | Meaning |
|---|---|
| **Session** | An agent identity. `POST /sessions {name}` returns a token and a lease (15 s). Any authenticated call renews the lease; `POST /sessions/heartbeat` renews it explicitly. An expired session loses its claims and its stick streams stop within 0.2 s. |
| **Claim** | A session's right to control an aircraft (`POST /vehicles/{id}/claim`). One claim per aircraft; claiming an aircraft held by another live session fails with `claimed_by_other`. |
| **Possession** | An operator flying the aircraft from the Relay window (keyboard, on-screen sticks or a gamepad). Possession always wins: it stops the agent's skill and sticks and **suspends** the claim. While suspended, every control call fails with `possessed_by_human` or `claim_suspended`. |
| **Hand-back** | When the operator releases, a live suspended claim becomes active again and Relay emits `relay_handback`. Relay sends nothing to the aircraft at that moment; the agent decides what happens next. |
| **Stop** | Emergency stop (`POST /vehicles/{id}/stop`): zero throttle for 50 ms, then a disarm request. It never changes who controls the aircraft. |

The `controller` field of each vehicle is `none`, `human` or `agent`.

An agent should therefore treat `possessed_by_human` and `claim_suspended` as "pause", watch the events for `relay_handback`, and re-read the vehicle state before continuing. `watch_handback.py` shows the pattern.

### Control levels and capabilities

| Level | Interface | Requires capability |
|---|---|---|
| 1 | `sticks` (roll, pitch, yaw, throttle) | `manual` (an autopilot heartbeat) |
| 2 | `arm`, `mode`, skills `takeoff`, `land`, `hold`, `move`, `yaw`; plans | `althold` for takeoff, hold, move and yaw |
| 3 | skills `goto`, `rtl`, ring courses; closed-loop `move` | `position` (a fresh local position estimate) |

Every vehicle reports `capabilities: {manual, althold, position}`. A missing capability fails with `capability_missing` or `no_position_estimate`. Simulators have all three. Real aircraft report `position` only with a local position source such as optical flow, motion capture or UWB.

### Agent flight level

Setting `agent_flight_level` (design 06 §5) decides what agent sessions may fly; only the operator changes it (Settings → Safety, or `PUT /settings` with the operator token). The operator in the window is never limited.

| Level | Agent sessions may |
|---|---|
| `sticks` (default) | Push sticks (WebSocket stream, `POST /vehicles/{id}/sticks`, the `sticks` skill), arm and disarm, switch to a manual mode (ArduPilot STABILIZE / ACRO, PX4 MANUAL / STABILIZED / ACRO; not DRIFT, which assists), switch a simulator's hover assist off (not on), fire, deploy and run onboard programs, and the safety actions: emergency stop and `land` (its events carry `safety`) |
| `full` | Everything in this guide, as in 0.3 |

At `sticks` the skills `takeoff`, `hold`, `move`, `yaw`, `goto`, `rtl`, `velocity` and `attitude`, plans that contain them, re-fly as a plan or a path, altitude, position and automatic modes, the flight commands of the device interface and RC overrides above channel 4 return 403 `sticks_only` with `detail.level = "sticks"` and `detail.action`. The flight MCP server lists only the tools that still work (13 of 20; it reads the setting on every `tools/list`), and Copilot drops the same tools and tells its model to write programs. Stable flight at this level is the job of an onboard program: the agent works at its own pace on the program, its parameters and its results, and the program closes the 50 Hz loop.

## 3. Frames and units

- **Position:** metres, East-North-Up: `x` east, `y` north, `z` up. All simulators share the frame `sim` (each spawns at a different grid point). Each real aircraft reports its own `local` frame, with its origin where the autopilot initialised its estimator.
- **Attitude:** radians; roll right-wing-down positive, pitch nose-up positive, yaw as a NED heading (0 north, clockwise positive). `heading_deg` is in degrees.
- **Sticks:** roll right +, pitch forward +, yaw clockwise +, each −1..1; throttle 0..1. In altitude-hold modes 0.5 holds altitude.
- **goto yaw and ring headings:** compass degrees (0 north, clockwise).
- **Safety volume:** a box, 3 × 3 × 2 m by default (`safety_volume` in the fleet snapshot), centred horizontally on the aircraft's origin with its floor at the origin. The origin is the spawn point for a simulator and the first arming point for a real aircraft. `goto` targets outside it fail with `outside_safety_volume`; ring courses are scaled to fit it.

## 4. Authentication

| Caller | Header | WebSocket query parameter |
|---|---|---|
| Agent session | `X-Relay-Session: <token>` | `?session=<token>` |
| Operator (the Relay window) | `X-Relay-Operator: <token>` | `?operator=<token>` |

Read-only endpoints need no token. The API binds 127.0.0.1 only and answers only requests addressed to `127.0.0.1` or `localhost`. Writes have three permission levels:

| Level | Caller | Covers |
|---|---|---|
| Controller | The session that claimed the aircraft; the operator | Sticks, arm, mode, skills, plans, re-fly, courses, stop, device commands (motors, actuators, RC override, raw commands, reboot, calibration, termination), parameter writes |
| App operation | The operator; any session while the `agents_app_control` setting is on (the default) | Network scan, connect by address, remove aircraft, add, remove and reset simulators, stop-all, bridge retry and setup, alert acknowledgement, course edits, settings changes, interface actions (`POST /app/ui`) |
| Operator only | The Relay window only | Possess and release over REST, stick-direction and propeller attestations, granting or withdrawing `agents_app_control` |

With `agents_app_control` off, app operations from a session fail with 403 `app_control_disabled`; a session that tries to change the setting itself gets 403 `operator_required`. Every interface action a session runs shows a notice in the window and is logged as an `app_command` event.

**Rate limits** per session: control calls (sticks, arm, mode, skills) 60 per second, other calls 20 per second. Excess calls return 429 `rate_limited` with `Retry-After: 1`.

| `GET /topology` | – | Station, vehicles, bridges, sessions, links and relative distances |

| `GET /courses` | – | Preset and custom ring courses (scaled to the safety volume) |
| `POST /sessions` | – | `{name}` → `{session_id, name, token, lease_s}` |

| `DELETE /sessions` | session | Close the session and release its claims |
| `GET /sessions` | – | Open sessions (no tokens) and their recent calls |
| `POST /vehicles/{id}/claim` | session | Claim |
| `POST /vehicles/{id}/unclaim` | session | Release the claim |
| `POST /vehicles/{id}/sticks` | controller | `{roll, pitch, yaw, throttle}`; repeat at 10–50 Hz |
| `POST /vehicles/{id}/arm` | controller | `{arm: true}` (real aircraft: `{arm: true, confirm: "ARM"}`) or `{arm: false}` |

| `POST /vehicles/{id}/skills/{name}` | controller | `takeoff {alt}`, `land`, `hold {seconds?}`, `move {forward?, right?, up?}`, `yaw {deg}`, `rtl`, `goto {x, y, z, yaw?}` |
| `POST /vehicles/{id}/plan` | controller | `{steps, name?, confirm?}`: run a sequence of skills (below) |
| `POST /vehicles/{id}/plan/cancel` | controller | Cancel the running plan; an airborne aircraft holds where it is |
| `GET /history/sessions/{sid}/refly` | – | What a flight record can be flown again from: `plan`, `path`, `sticks` and `recommended` |

| `POST /vehicles/{id}/course/stop` | controller | Abort the course |
| `POST /vehicles/{id}/stop` | controller | Emergency stop |
| `POST /sims/{id}/assist` | controller or operator | `{on}`: hover assist of a simulated aircraft (below); `sim_only` for a real aircraft |
| `PUT /sims/{id}/airframe` | controller or operator | `{preset \| params, seed?}`: airframe defects of a simulated aircraft (below) |
| `GET /sims/{id}/airframe` | controller or operator | The full airframe values, their limits and the hover throttle |

### Skills

A skill call returns at once with `{"skill": {"id", "name", "state": "running", "detail"}}`. The vehicle's `skill` field then reports the same `id` with `state` `running`, `done` or `failed`; events `skill_started`, `skill_finished` and `skill_failed` carry `data.skill_id`. Starting a new skill replaces the running one. The SDK waits on the id for you.

| Skill | Requires | Behaviour |
|---|---|---|
| `takeoff {alt}` | althold | Arms a simulator if needed, climbs to `alt` metres above the take-off point (0.2 m to the safety-volume height) and holds. With a position estimate it uses the autopilot's take-off (GUIDED / OFFBOARD); without one it climbs in ALT_HOLD / ALTCTL on the throttle stick and levels off on the barometer altitude. A real aircraft on the ground must be armed first, or the call must carry `confirm: "ARM"` and pass preflight. Already airborne: finishes immediately. |
| `land` | any | Lands in place; finishes when the aircraft is on the ground and disarmed. |
| `hold {seconds?}` | althold | Holds position (LOITER / POSCTL) or altitude (ALT_HOLD / ALTCTL). With `seconds`, reports `done` after that time and keeps holding. |
| `move {forward?, right?, up?}` | althold, airborne | Metres in the aircraft's body frame (negative values go back, left, down). With a position estimate: a closed-loop `goto` to the target. Without one: **open loop**, a timed tilt with a dead-reckoned distance estimate (about ±30 %), horizontal distance at most 2 m per step; `up` uses the barometer altitude. |
| `yaw {deg}` | althold, airborne | Turns by `deg` degrees, positive clockwise, on the attitude heading; finishes within 3°. |
| `rtl` | position | Returns to the launch point and lands. |
| `goto {x, y, z, yaw?}` | position | Flies to the target in the vehicle's position frame; finishes within 0.15 m. |
| `sticks {roll, pitch, yaw, throttle, seconds}` | manual, armed | Holds one stick position for `seconds` (0.05–10 s) in a manual mode, then centres the sticks. Lets a language model give short manual inputs. |
| `attitude {roll_deg, pitch_deg, yaw_rate_dps, thrust, seconds}` | manual, armed | Holds an attitude and collective thrust with `SET_ATTITUDE_TARGET` for `seconds` (ArduPilot switches to GUIDED_NOGPS, PX4 to OFFBOARD). |
| `velocity {vx, vy, vz, yaw_rate_dps?, seconds}` | position | Flies an ENU velocity (m/s) for `seconds`, then holds. |

While a skill runs or holds, Relay streams neutral sticks (throttle 0.5) as an RC keep-alive so the autopilot's RC-loss failsafe stays quiet; see `hardware.zh-CN.md` for the failsafe settings this relies on.

### Plans

A plan is an ordered list of up to 24 steps, each one skill, run one after another by Relay:

```json
POST /api/v1/vehicles/sim-1/plan
{"name": "bench", "steps": [
  {"action": "takeoff", "alt": 1.0},
  {"action": "hover", "seconds": 3},
  {"action": "move", "forward": 1},
  {"action": "move", "forward": -1},
  {"action": "yaw", "deg": 45},
  {"action": "land"}
]}
```

Actions: `takeoff {alt}` (default 1 m), `hover {seconds}` / `hold {seconds}` (default 3 s), `move {forward, right, up}`, `yaw {deg}`, `land`, `goto {x, y, z, yaw?}`, `rtl`, and `sticks`, `attitude` and `velocity` (parameters as in the table above). Every step is validated before the plan starts (`invalid_request` names the step and field; a step whose capability is missing fails with `capability_missing`). A plan that does not start with `takeoff` needs the aircraft in the air (`not_airborne`). On a real aircraft a plan that starts on the ground needs `confirm: "ARM"`.

The vehicle's `plan` field reports `{id, name, state, index, count, steps, results, detail}` with `state` `running`, `done`, `failed` or `cancelled`; events `plan_started`, `plan_step`, `plan_finished`, `plan_failed` and `plan_cancelled` mark progress. A step that fails, a new skill, sticks from the controller, an operator moving a stick or possessing the aircraft, and a stop all end the plan. `POST /plan/cancel` ends it on purpose (`no_plan` if none is running) and leaves an airborne aircraft holding.

`sdk/python/examples/bench_routine.py` flies the sequence above: `python3 sdk/python/examples/bench_routine.py --vehicle sim-1`; on a real aircraft add `--arm-real`.

### Re-fly (fly a past flight again)

Every flight records its plan, its track and its sticks (with their source: keyboard, gamepad, on-screen sticks or an agent). `GET /history/sessions/{sid}/refly` lists what a record offers; `POST /vehicles/{id}/refly` flies it again on any aircraft:

| `mode` | Behaviour |
|---|---|
| `plan` | The recorded plan, with the same steps and parameters |
| `path` | The recorded track as `goto` waypoints every 0.3 m, translated to the target's current position and flown as a plan; needs `position` |
| `sticks` | The sticks and mode changes from arming to disarming on the original time axis, scaled by `speed` (0.25–2.0); only for records flown in a manual mode |
| `auto` (default) | The first of `plan`, `path` and `sticks` the record offers |

`plan` and `path` return `{plan}`; `sticks` runs as the `replay` skill and returns `{skill}`. Follow them like any plan or skill; events `refly_started`, `refly_finished` and `refly_failed` mark the run. A missing record fails with `record_not_found`, a record without the requested source with `refly_unavailable`. A real aircraft that starts on the ground needs `confirm: "ARM"`; an operator takeover, stick input or a stop ends the re-fly.

### Device-level interface

The device-level interface reaches down to individual motors, output channels and MAVLink messages. Writes need the controller (claim first); calls that change the hardware state need a confirm word:

| Confirm word | For | When |
|---|---|---|
| `MOTOR` | Motor test, actuator commands that drive a motor output | Real aircraft |
| `ARM` / `FORCE` | Arm / force-arm (skips prearm checks) | Real aircraft |
| `REBOOT` | Reboot the autopilot | Real aircraft |
| `CALIBRATE` | Sensor calibration | Real aircraft |
| `TERMINATE` | Flight termination | Every aircraft, simulators included |

Motor tests, reboots and calibrations need the aircraft disarmed, otherwise 409 `must_be_disarmed`.

| Method and path | Auth | Purpose |
|---|---|---|
| `GET /vehicles/{id}/device` | – | Device overview: motor count, layout and per-output PWM, servo outputs, RC channels, frame type, sensor health, estimator status, vibration, home, parameter table counts, receive rate of every message |
| `GET /vehicles/{id}/messages/{name}` | – | The newest frame of one MAVLink message (fields, time, rate), for example `SERVO_OUTPUT_RAW` or `EKF_STATUS_REPORT` |
| `GET /vehicles/{id}/params/{name}` | – | One parameter; read by name from the autopilot (up to 2 s) when the table lacks it, else `param_not_found` |
| `POST /vehicles/{id}/params/read` | session | `{names}` (up to 32) read by name → `{values, missing}` |
| `POST /vehicles/{id}/params` | controller | `{name, value, confirm}`; `confirm` must equal the name |
| `GET /commands` | – | Raw command catalogue: MAV_CMD name and number, English and Chinese labels, parameter meaning and range, danger level, autopilots |
| `POST /vehicles/{id}/command` | controller | `{command, params[≤7], frame?, use_int?, confirm?, timeout_s?}`; catalogue commands only (`command_not_allowed`); returns the `COMMAND_ACK`. `DO_MOTOR_TEST` and `ACTUATOR_TEST` keep the motor-test limits (0.2–5 s, at most 30 % on a real aircraft) |
| `POST /vehicles/{id}/motors/test` | controller | `{motor: number or "all", throttle_pct, seconds (0.2–5), confirm}`; at most 30 % throttle on a real aircraft |
| `POST /vehicles/{id}/motors/stop` | controller | Stop a motor test now |
| `POST /vehicles/{id}/actuators/set` | controller | `{index 1–16, value −1..1 or pwm 800–2200, seconds, confirm?}`; `seconds` 0 holds until changed. Outputs 1 to the motor count are motors: `MOTOR`, a disarmed aircraft, `seconds` 0.2–5 and at most 30 % on a real aircraft |
| `POST /vehicles/{id}/rc` | controller | `{channels: {"1".."18": 1000–2000}}` or `{axes}`: one RC-override frame, expires after 0.8 s, replaces sticks |
| `POST /vehicles/{id}/message-interval` | controller | `{message, hz 0–50}`; 0 stops the stream |
| `POST /vehicles/{id}/request-message` | controller | `{message}`: ask the autopilot to send it once |
| `POST /vehicles/{id}/reboot` | controller | `{confirm}`: reboot the autopilot; the link comes back on its own |
| `POST /vehicles/{id}/calibrate` | controller | `{sensor: gyro | level | baro | accel_simple, confirm}` |
| `POST /vehicles/{id}/home` | controller | `{here: true}` or `{lat, lon, alt}` |
| `POST /vehicles/{id}/terminate` | controller | `{confirm: "TERMINATE"}`: motors stop at once and the aircraft is force-disarmed; an airborne aircraft falls |

Mode lists, arm, disarm and mode changes use the section 5 endpoints; `GUIDED_NOGPS` is available on ArduPilot.

### Application control

Application control lets an agent operate Relay itself: read and change the window, manage the fleet and the network, change settings. Interface actions run in the open Relay window, so the window must be running; the other app operations are carried out by the backend.

| Method and path | Auth | Purpose |
|---|---|---|
| `GET /app` | – | App overview: version, uptime, ports, scan state, counts of aircraft, sessions, controllers and alerts, whether a window is connected, `agents_app_control` |
| `GET /app/ui` | – | What the window shows: language, workspace, selected aircraft, view, inspector, dialogs, preferences, controllers and bindings, possession, window size, open record |
| `GET /app/gamepads` | – | Connected controllers and the aircraft they are bound to |
| `GET /app/actions` | – | Catalogue of interface actions and their arguments |
| `POST /app/ui` | app operation | `{action, args}`: run one interface action, waiting up to 5 s → `{ok, data}` |

Interface actions: `get_state`, `set_language {lang: en | zh}`, `set_workspace`, `select_vehicle {vehicle | null}`, `set_view`, `open_inspector`, `close_inspector`, `open_settings`, `open_connect`, `close_dialogs`, `set_pref`, `notify {text, level}`, `bind_gamepad`, `unbind_gamepad`, `possess`, `release`, `open_record`, `replay {play | pause | seek}`, `toggle_copilot`, `window {focus | minimize | maximize | restore | fullscreen}`, `screenshot {max_width}`. The `possess` action runs in the window and is the same as the operator possessing there: a person then flies the aircraft and agent claims are suspended.

Without a connected window the call fails with 503 `ui_unavailable`; no answer within 5 s gives 504 `ui_timeout`; an action the window refuses gives 409 `ui_action_failed`. Fleet, network, settings and alert operations use the existing paths in section 5 and the OpenAPI reference (`/discover`, `/vehicles`, `/sims`, `/stop-all`, `/network/retry`, `/bridges/{ip}`, `/alerts/{id}/ack`, `/courses/{id}`, `/settings`) at the "app operation" level of section 4.

### Bench procedures

A bench procedure runs calibration and stability checks on one aircraft step by step and saves a report (S1 link and firmware, S2 battery at rest, S3 parameter baseline, S4 sensor calibration, S5 stick directions, S6 motor order and direction, S7 ground vibration, S8 propellers fitted, S9 hover test, S10 step response, S11 hover learning, S12 report). Procedures: `full_bench` (S1–S12), `preflight_quick` (S1, S2, S7, S9 for 10 s, S12), `motor_check` (S1, S6, S12), `vibration_check` (S1, S7, S9 for 20 s, S12) and `hover_tune` (S1, S8–S12). A procedure starts on a disarmed aircraft on the ground and needs control of it (claim, or the operator's possession).

| Method and path | Auth | Purpose |
|---|---|---|
| `GET /procedures` | – | Catalogue: `{procedures: [{id, title_en, title_zh, steps: [{id, title_en, title_zh, kind}], est_s}]}`; `kind` is `auto`, `operator`, `operator_device`, `device` or `flight` |
| `POST /vehicles/{id}/procedure` | controller | `{procedure, options: {hover_s 5–60, skip: [step ids], auto_answer}}`; `auto_answer` (simulators only) answers S6 from the servo outputs; S12 cannot be skipped → the run view |
| `GET /vehicles/{id}/procedure` | – | The current run, else the most recent saved one: `state` (`running`, `waiting`, `passed`, `warned`, `failed`, `aborted`), `step`, `index`, `total`, `paused`, `reason`, and per step `state`, `verdict`, `metrics` (value, unit, level, window `mean` / `peak`, `warn` / `bad` limits), `findings`, `suggestions`, `prompt`, `live` (recent points of the running step, 5 Hz) |
| `POST /vehicles/{id}/procedure/answer` | controller or operator | `{step, answer, confirm?}`: answer the waiting prompt; `answer` is one of `prompt.answers[].id` |
| `POST /vehicles/{id}/procedure/abort` | controller or operator | Abort: motor tests stop and an airborne aircraft lands |
| `GET /test-runs?vehicle=&limit=` | – | Saved reports, newest first, with verdict counts; `vehicle` matches the aircraft id or its address |
| `GET /test-runs/{run_id}` | – | One saved report with every step and the parameter baseline and changes |
| `GET /test-runs/{run_id}/export?fmt=md\|json` | – | The report as Markdown (bilingual tables, UTC times) or JSON, as a download |

A waiting step carries `prompt`: `{id, text_en, text_zh, detail_en, detail_zh, answers, confirm_word, operator_only, data}`. On a real aircraft `confirm_word` keeps the device rules: `MOTOR` before S6 and S7 spin motors (props off, at most 30 %, at most 5 s, disarmed; one word covers every motor of the step), `CALIBRATE` for each S4 calibration, `ARM` before S9 takes off, and the parameter name before S11 writes it (read back and checked). Prompts with `operator_only: true` (S5, S6, S8 and the S7 propeller check on a real aircraft) refuse sessions with 403 `operator_required`: a person must attest them at the Relay window. On a simulator an agent may answer every prompt.

The run is driven by the fleet loop, not by the caller: poll `GET .../procedure` (or watch the events) and answer when `state` is `waiting`. A run aborts on an emergency stop (the stop wins: no procedure landing follows), a lost link, a crash, a lost claim, or arming and disarming outside the flight steps. A session's run pauses while a person possesses the aircraft and resumes, from the start of the current step, once control returns and the aircraft is disarmed. Flight steps take off to 0.6 m, keep inside the safety volume and land by themselves; S10 flies short roll, pitch and yaw stick steps in altitude hold. On a simulator with hover assist off (no barometer or position source) S9 and S10 fail at once with the finding `hover_assist_off`, and a flight segment whose simulator loses hover assist in the air lands and fails. Suggested parameter changes (S10 rate gains, S11 hover throttle) are never written automatically: S11 asks for each one.

### Flight health

Every vehicle carries `health`: rolling diagnostics over the last 5 s, shown in the inspector under Overview → Flight health. `state` is `ok`, `warn`, `bad` or `idle` (not armed); `items` lists `{key, level, value, unit, detail}` for `oscillation` (roll and pitch rate RMS, deg/s), `lean` (tilt held with centred sticks), `yaw_drift`, `alt_hold` (vertical speed spread in altitude hold), `hover_throttle`, `motors` (spread of mean motor outputs, saturation), `vibration` (peak, accelerometer clipping), `battery_sag` (per cell), `link` and `stick_stream` (stick updates from the Relay window while a person flies). Flight items are judged only after 1.5 s in the air; `level` is `na` until then. [`flight-tuning.zh-CN.md`](flight-tuning.zh-CN.md) explains each item and what to change.

### Sticks

Stick frames older than 0.8 s stop being sent, so the aircraft never flies on stale input. For continuous control, send at 10–50 Hz over REST or, better, over the WebSocket (`{"type": "sticks", "vehicle", "roll", "pitch", "yaw", "throttle"}`). Closing the WebSocket stops every stick stream it was feeding. MCP offers no continuous stick stream: a language model cannot close a 50 Hz loop; `relay_sticks_for` and the `sticks` skill hold one stick position for at most 10 s, then centre the sticks.

### Ring courses

`course/start` places the course at the vehicle's origin and returns it, including `rings` in the vehicle's frame: `c` (centre `[x, y, z]`), `yaw_deg` (compass heading of the ring normal) and `r` (radius). The clock starts at take-off. A ring counts when the aircraft crosses its plane inside the radius, in order. The vehicle's `course` field reports `next`, `total`, `splits`, `elapsed_s` and `best_s`; events `ring_passed` and `course_finished` mark progress. `course_sim.py` flies 0.35 m before and after each ring along its normal.

### Simulator hover assist

Every simulated aircraft has `hover_assist` (default: setting `sim_hover_assist`, on). On, it flies as before: ALT_HOLD holds height, LOITER holds position, GUIDED, RTL and LAND are autonomous. Off, it is a racing quad without barometer or position source: the attitude still self-levels, but the throttle is thrust (no height hold, no tilt or voltage compensation, the hover point rises as the battery sags), ground effect, motor lag, turbulence (setting `sim_turbulence`, 0–1) and propeller wake act, the aircraft reports no barometer and no position estimate (`capabilities.althold` and `position` false), and ALT_HOLD, LOITER, GUIDED, RTL and AUTO are refused with `Mode requires hover assist`. LAND stays as the failsafe and descends open loop. The switch is allowed armed and in flight: off moves an airborne aircraft to STABILIZE with a 0.3 s thrust ramp; on enters ALT_HOLD at the present height.

`POST /sims {count, autopilot, position, hover_assist}` sets it at creation; `POST /sims/{id}/assist {on}` switches it (the operator, the controlling session, or any session while nobody controls the aircraft and the operator allows app control). The snapshot carries `vehicle.sim = {hover_assist, turbulence}` (null on real aircraft); event `sim_assist_changed` reports a change. MCP: `app_sim_assist`; SDK: `sim_assist(id, on)` and `add_sims(count, autopilot, hover_assist)`.

### Simulator airframe defects

With hover assist off a simulated aircraft also flies with the assembly defects of a real one (design 06 §4). With hover assist on they wait; the assisted model is unchanged.

| Value | Range | Effect |
|---|---|---|
| `mass_kg`, `payload_kg` | 0.08–0.30, 0–0.20 kg | Take-off weight: the hover throttle rises (0.12 kg hovers at 0.50, 0.16 kg at about 0.63); above the thrust limit (0.288 kg) the aircraft cannot lift |
| `cg_offset_cm` | [forward, right], ±3 cm | The angle loop leans toward the CG (2.5° per cm); airborne, its integrator removes 70 % of that with a 2 s time constant, the remaining 30 % is a steady tilt, so the aircraft drifts toward the CG. The integrator resets on the ground. A large offset saturates motors and the uncorrected remainder grows |
| `level_trim_deg` | [roll, pitch], ±5° | Level calibration error: with centred sticks the aircraft flies this much tilted while ATTITUDE reads level, so it drifts. The accelerometer (SCALED_IMU) still feels the push before drag builds up |
| `motor_gain` | 4 × ±0.08 | Efficiency deviation of motors 1–4 (ArduPilot X order): yaw drift (same 70 % / 2 s correction) and a small tilt disturbance; the motor outputs in SERVO_OUTPUT_RAW differ |
| `prop_damage`, `damaged_prop` | 0–1, motor 1–4 | That propeller loses up to 30 % thrust; VIBRATION rises by up to 50 m/s² at full throttle, accelerometer and gyro noise rise, the attitude jitters |
| `imu_noise` | 0–5 | Noise multiplier on ATTITUDE (0.08° roll and pitch, 0.15° yaw, 0.6°/s rates at 1) and SCALED_IMU (0.06 m/s²) |

Presets, generated deterministically from a seed (0 – 2^31−1): `ideal` (all zero: exactly the hover-assist-off model), `typical` (default: CG within 0.25 cm, level error within 0.4°, motors within 2 %, noise ×1), `rough` (CG 0.7–1.4 cm, level error 1–2°, motors within 8 %, one propeller 20–50 % damaged, 5–20 g payload, noise ×2: a naive hover drifts several metres in 20 s) and `custom` (explicit values).

`PUT /sims/{id}/airframe` takes `{preset}` (a fresh seed), `{preset, seed}`, `{seed}` (re-roll the current preset; a custom airframe keeps its values) or `{params: {...}}` (any subset, overlaid on the named preset or on the current values, which makes it `custom`). Allowed armed and in flight; the integrator starts again from zero. It returns, like `GET`, `{id, preset, seed, params, active, hover_throttle, limits}`; `hover_throttle` is the level hover throttle out of ground effect at full battery, null when the aircraft cannot lift. Who: the operator, the controlling session, or any session while nobody controls the aircraft and the operator allows app control; `sim_only` for a real aircraft, `invalid_request` names the bad field. `POST /sims` takes the same body as `airframe` (every new aircraft of the call gets it); without it each new simulator takes the setting `sim_airframe_default` (`ideal` | `typical` | `rough`, default `typical`) with a fresh random seed.

The snapshot carries only `vehicle.sim.airframe = {preset, seed}`: the values are never in the snapshot or in a program's observation; they show in flight. Event `sim_airframe_changed` (`data.preset`, `data.seed`, `data.by`). Simulators answer `SCALED_IMU` (board FRD specific force in mG, rates in mrad/s) when asked with `SET_MESSAGE_INTERVAL` or `REQUEST_MESSAGE`; it is in no stream group.

### Onboard programs

An onboard program (design 06 §2) is a restricted Python program with `PARAMS`, `init(ctx)` and `step(obs, ctx) -> Sticks` that Relay runs in an isolated program host at 50 Hz on the aircraft's stick path. It sees only what the aircraft measures (`obs`: attitude, rates, accelerations, barometric height, optional position, battery, motor output, arena state, contacts) and outputs the four sticks and the trigger. [`programs-guide.md`](programs-guide.md) is the compact reference for writing one (the same text is in Copilot's instructions and in the MCP tool `program_guide`); [`programs.md`](programs.md) is the full documentation.

| Method and path | Who | Purpose |

| `PUT /programs/{pid}` | session or operator | `{source}` or `{patch: [{start, end, text}]}` (1-based, inclusive, numbered against the current revision; `end = start - 1` inserts), plus `name`, `description`, `params`, `tests`, `note`: a new revision; returns `{program, validation}` |
| `DELETE /programs/{pid}` | session or operator | Delete a stored program |

| `POST /programs/{pid}/test` | session or operator | `{rev?, source?, tests?, seed?}`: run the unit tests, `{results, passed, total}` |

The snapshot carries `vehicle.program` (`{id, name, rev, state, status: running | paused | faulted | stopped, fps, faults, last_error, mode, ...}`) and `programs_allowed`. Rules that always hold: a person who possesses the aircraft pauses a `pilot` program and releasing never resumes it; emergency stop, link loss and a crash stop it; the claim ending, the session's own sticks and any skill or plan supersede it; stale sticks time out after 0.8 s as before. Real aircraft accept a program only while the operator's **Allow programs on this aircraft** switch is on and preflight passes, and their `fire` output is ignored.

### Challenges and duels

Onboard programs (design 06 §2) are judged like exercises on a practice site: a **challenge** is a fixed scenario with a scoring rule, a **duel** sets 2–8 programs against each other in the arena. Both run in a **headless evaluator**: a separate worker process that builds an isolated fleet (no sockets, nothing on disk, an injected clock) and steps the same simulated autopilot, airframe defects, stick path, arena rules and program engine as live flight, as fast as the machine allows (about 12× real time with one aircraft, 5–7× with two). Hover assist is always off. The same scenario, seeds and program revisions always give the same result. At most two jobs run at once; the rest wait in a queue of 16.

| Method and path | Auth | Purpose |
|---|---|---|
| `GET /challenges` | – | `{challenges: [{id, kind, name_en, name_zh, goal_en, goal_zh, scene_en, scene_zh, duration_s, visible_seeds, hidden_seeds, opponent, best, attempts}]}` |
| `GET /challenges/{id}` | – | Adds `scoring_*`, `sensors`, `hover_assist`, `info` (corners, rings and other public parameters) and the last 20 submissions in `history` |
| `POST /challenges/{id}/submit` | session or operator | `{program, rev?, params?, visible_only?}` → `{job}`; every visible and hidden seed, or only the visible ones with `visible_only` (not counted as best) |
| `POST /duels` | session or operator | `{programs: [id or {program, rev?, params?}, …2–8], rounds? (1–20, default 3), seed? (default 1), scenario?: {duration_s (10–180), arena, airframe (ideal / typical / rough), sensors, turbulence}}` → `{job}` |
| `GET /jobs`, `GET /jobs/{id}` | – | `{job: {id, kind, state (queued / running / done / failed / cancelled), progress, queue_position, programs, result, error}}` |
| `DELETE /jobs/{id}` | session or operator | Cancel a queued or running job (its worker is stopped) |
| `GET /ladder` | – | `{ladder: [{rank, program, name, rating, games, wins, draws, losses}], duels}` (Elo, start 1200) |
| `GET /traces/{id}` | – | A replay trace (below) |

| Challenge | Scenario | Passes when |
|---|---|---|
| `liftoff` | Payload: hover throttle about 0.62; barometer, no position | Off the ground within 5 s, then 3 s without a break at 1.0 ± 0.2 m |
| `hover` | CG forward of the middle and a level error; barometer, no position | From 6 to 26 s: drift ≤ 0.8 m and height 1.0 ± 0.25 m (judged on the truth) |
| `heading` | Unequal motor efficiencies (yaw drift) | From 5 to 20 s: heading within 10° of the spawn heading, at least 0.4 m up |
| `square` | UWB-like position (10 Hz, σ 5 cm) | The four corners of `info.corners` (radius 0.4 m) in order within 40 s; faster scores higher |
| `rings` | The `cage-loop` ring course, UWB-like position | Every ring in order within 60 s; timed |
| `pursuit` | A scripted target circles the centre (3 m, 0.5 m/s, 1.2 m up); contacts and UWB-like position | Within 2 m of the target for at least half of the 60 s; the score is that share |
| `duel_easy` / `duel_medium` / `duel_hard` | One against one with `hunter_easy` / `hunter_medium` / `hunter_hard` (arena radius 8 m, ceiling 4 m) | A win: the opponent shot down, crashed or out of the arena while you still fly; time up scores by hit points left |
| `ram_easy` | A target hovers on the spawn ring (`judge_hover_target`); guns are off; contacts and UWB-like position | The target crashes from a collision with you within 60 s; faster and harder impacts score higher, a near miss scores by the closest approach |

Scores are 0–100. A submission runs every seed, passes when every seed passes and scores their mean; `result = {score, passed, metrics, seeds: [{seed (null when hidden), hidden, score, passed, metrics, trace_id}], trace_id, best, speed}`. Hidden seeds fly other airframes and leave no trace. Each challenge keeps its best full submission and the last 50 in `<data_dir>/programs/results.json`.

A duel round puts one aircraft per program on a ring of spawn points around the arena centre (shuffled and with airframes seeded by `seed + round − 1`), all facing the centre. An aircraft is out when it is shot down, crashes or leaves the arena box; the round ends when one is left (after one second) or the time is up. Placement: still flying first, then survival time, hit points, hits. The last aircraft flying wins the round; otherwise it is a draw. The ladder (`<data_dir>/programs/ladder.json`) moves by pairwise Elo over each round's placements (K = 32, split over the other entrants). `result = {rounds: [{round, seed, winner, draw, duration_s, aircraft: [{id, program, alive, hp, hits, hits_taken, survived_s, reason, place}], trace_id}], standings, ladder: [{program, rating, delta}], speed}`. Event `judge_finished` (`data.job`, `data.state`, `data.score`, `data.passed`) when a job ends.

A **trace** (`GET /traces/{id}`, gzip on disk, the newest 300 kept) replays every aircraft of one seed or round at 10 Hz: `{id, job, version: 1, kind, challenge?, round?, scenario, seed, hz, duration_s, fields: ["x", "y", "z", "roll", "pitch", "yaw", "throttle", "hp", "flags"], arena, course, markers, t: [...], aircraft: [{id, label, program, rev, name, role, team, spawn, frames: [[…one row per t…]], states: [[t, state]]}], shots: [{id, shooter, t0, p, v}], events: [{t, kind, vehicle, …}], result}`. Positions are world ENU metres with the arena centre at the origin (the snapshot's frame), attitude in radians (yaw is the compass heading 0..2π), `flags` bits 1 armed, 2 airborne, 4 shot down, 8 crashed, 16 out. A shot leaves `p` at `t0` with velocity `v` and follows the arena ballistics (`web/src/arena/ballistics.ts`). Events: `hit`, `down`, `crash`, `out`, `liftoff`, `corner`, `ring`, `course_finished`, `program_faulted`, `program_stopped`. The full contract is in the `relay.judge` module docstring and in `Trace` of `web/src/api/schema.json`.

The SDK, the MCP tools and Copilot report `judge_unavailable` when they talk to a Relay older than 0.4.0, which has none of these routes.

### Program workflow

The loop an agent goes through, here with the SDK at the default `sticks` level (the MCP tools and Copilot's tools have the same names: `program_create`, `program_update`, `program_validate`, `program_test`, `challenge_submit`, `program_deploy`, `program_params`, ...):

```python
with RelayClient() as relay:
    relay.open_session("my-agent")
    # 1. write: start from the built-in hover_trim
    pid = relay.program_create("My hover", copy_of="hover_trim", note="start")["program"]["id"]
    relay.program_update(pid, patch=[{"start": 14, "end": 14, "text": '    "target_alt": 1.2,'}], note="higher")
    # 2. validate: language rules, line and column of each problem
    assert relay.program_validate(pid)["ok"]
    # 3. test: the unit tests in the program host
    print(relay.program_test(pid))
    # 4. submit to a challenge (headless, hidden seeds)
    print(relay.challenge_submit("hover", pid)["result"])
    # 5. deploy on a simulator with physical flight and a rough airframe
    relay.claim("sim-1")
    relay.sim_assist("sim-1", False)
    relay.mode("sim-1", "STABILIZE")
    relay.arm("sim-1")
    relay.program_deploy("sim-1", pid, airframe={"preset": "rough", "seed": 7})
    # 6. watch and tune live; stop when done
    print(relay.program_status("sim-1"), relay.program_log("sim-1")["lines"][-5:])
    relay.program_params("sim-1", ki=0.2)
    relay.program_stop("sim-1")
```

Every edit is a new revision with its author (`operator` or the session name) and note, so a result can always be traced to the code that produced it. Tune parameters live first; change code when the structure is wrong; resubmit to the challenge, whose hidden seeds catch a program tuned to one airframe.

### LAN arena

The arena (05 §7) lets Relay terminals on the same broadcast domain see each other's simulated aircraft, fire virtual rounds at them, and score hits. It is joined from the window (top bar **Arena**, setting `peer_enabled`) and uses one UDP socket of its own (setting `peer_port`, default 47114, multicast `239.255.71.14` with TTL 1 plus subnet broadcast). Nothing received from the network reaches a control path: no stick, arm, claim, parameter, skill, plan or device call is ever driven by a peer packet. **Real aircraft never join the arena and are never affected by virtual rounds**: only simulators are shared, can fire and can be hit.

| Method and path | Who | Purpose |
|---|---|---|
| `GET /arena` | – | `{enabled, instance, seat, callsign, error, peers: [{id, callsign, seat, rtt_ms, stale, score, vehicles}], shots, local: {ammo, hp, reloading, reload, down, max_ammo, max_hp, score}}`; positions are already in this terminal's local ENU frame |
| `POST /vehicles/{id}/fire` | controller | `{seconds}` (0–3, default 1; 0 releases): hold the trigger of an armed, airborne simulator; 8 rounds/s, 24 per magazine, 1.5 s reload; `arena_off` outside the arena, `arena_down` after a shoot-down, `sim_only` for a real aircraft |

A round deals 20 damage (five bring a simulator down) and pushes the airframe; a shot-down simulator stops its motors, falls, disarms on the ground and returns to its seat's spawn point after 5 s (setting `arena_auto_respawn`) or on a reset. Hits are not safety events: they raise no alert. Settings: `peer_enabled`, `peer_port`, `peer_callsign` (≤ 16 characters; empty uses the computer name), `arena_auto_respawn`. SDK: `arena()`, `fire(id, seconds)`.

### Dogfights, matches and the leaderboard

A **dogfight** (07 §3) is a timed fight of 2–8 simulators in the arena, each flown by an onboard program at the `sticks` level: **gunners** fire, **rammers** fly into their targets and never fire. One call sets it up: Relay takes free simulators (and adds the rest), places them on a ring of spawn points 3 m inside the arena edge facing the centre, sets hover assist and the airframe, opens a session named `dogfight` that claims them, deploys the program of each role (`hunter_medium` and `rammer` by default), arms them, and the programs take off themselves. The operator can possess any aircraft at any time: its program pauses (state `human`) and resumes on release. With `respawn` a shot-down or crashed aircraft (state `down`) is back at its spawn point after 5 s and flies again. At the end (time up, `DELETE`, or every aircraft failed) the programs stop, airborne aircraft land, a simulator still up after 20 s or sitting on the ground without the landing detector firing is disarmed with the checks skipped, the claims are released and the final standings stay on the leaderboard. On the LAN the dogfight joins the running match or starts one on every version 2 terminal; with the arena off it runs in **practice mode** (the arena rules without a socket; nothing is sent) and leaves it at the end. **Real aircraft are refused** (`dogfight_real_aircraft`); they never take part in matches, collisions or scenarios.

| Method and path | Who | Purpose |
|---|---|---|
| `POST /scenarios/dogfight` | app control (session with `agents_app_control`, or the operator) | `{aircraft (2–12, default 6; more than 8 → dogfight_no_aircraft), teams ("ffa" / 2 / 3), roles: {gunner, rammer} (sum = aircraft; default 2 gunners : 1 rammer), programs: {gunner, rammer}, arena: {radius (3–30, default 8), ceiling (2–10, default 4)}, airframe (ideal / typical / rough), hover_assist (default false), duration_s (30–1800, default 180), respawn (default true), seed, vehicles}` → the dogfight view; `dogfight_running` while one runs |
| `GET /scenarios/dogfight` | – | `{running, phase (idle / booting / arming / deploying / running / ending / done), started_at, ends_at, config, aircraft: [{vid, role, program, team, state (booting / arming / deploying / flying / human / down / stopped / failed)}], match, by, reason (time / stopped / error), error}` |
| `DELETE /scenarios/dogfight` | app control | End it early; `dogfight_not_running` without one |
| `POST /arena/match` | app control | `{duration_s}` (30–1800, default 180): a match here and on every version 2 peer; `arena_off`, `match_running` |
| `DELETE /arena/match` | app control | End the running match everywhere (`ended: true`); without one, reset the statistics (`ended: false`) |
| `GET /arena/leaderboard?by=` | – | `{by, match, rows: [{key, aircraft, callsign, local, controller: {kind (program / agent / human / none), name}, downs, hits, shots, accuracy, rams, deaths, crashes, damage, alive, alive_s, best_alive_s}]}`, sorted by `downs` (default), `survival`, `accuracy` or `rams` |

**Statistics.** Every simulator in the arena has a line: downs (a round of its brought another aircraft down), hits, shots, rams (a collision it caused crashed the other aircraft), deaths (shot down), crashes (collision or ground), damage dealt, the current survival time and the longest one. A match (`{id, origin, started_at, duration_s, running, ended_at, reason (time / stopped / conflict)}`) resets the lines at its start and freezes them at its end; the arena snapshot carries `match` and `board_rev`. Rows of a LAN peer come from its own statistics (it counts what it saw); a Relay 0.4 peer's rows have null statistics.

**Wire protocol 2.** Relay 0.5 speaks version 2 of the arena protocol and stays compatible with 0.4: every packet 0.4 knows is still sent with version byte 1, byte for byte; version 2 is used only for `COLLIDE`, `MATCH` and, about once a second, a `STATE` that carries the statistics block (a 0.4 terminal drops those as malformed and keeps the other states). A peer is version 2 from its first valid version 2 packet; matches and collisions only involve version 2 peers. `MATCH` starts or ends a match on every terminal (the earliest start wins a conflict; it is repeated every 2 s while running). **LAN collisions**: each terminal sweeps its own aircraft against the peers' (as last reported, extrapolated at most 0.15 s); on a contact it applies the response to its own aircraft and sends `COLLIDE` to the owner of the other one. The owner applies it only after checking it again: at most 0.3 s old (clock difference and half the round trip), the two aircraft within 0.6 m of each other at the contact time on its own view, at most 4 per second per peer aircraft, once per pair within 0.5 s; it answers with a reply (never answered again) so the sender learns about a crash it caused. A rejected `COLLIDE` changes nothing. Event `collision` (`data.a`, `data.b`, `data.b_label`, `data.point`, `data.v_rel`, `data.crashed`, `data.kind`, `data.remote`).

SDK: `dogfight_start(...)`, `dogfight_stop()`, `dogfight_status()`, `leaderboard(by)`, `match_start(duration_s)`, `match_end()`. MCP (application server) and Copilot: `dogfight_start`, `dogfight_stop`, `dogfight_status`, `leaderboard`. A request such as "a six-aircraft free-for-all, four gunners and two rammers" maps to `dogfight_start {aircraft: 6, teams: "ffa", roles: {gunner: 4, rammer: 2}}`.

## 6. WebSocket `/api/v1/stream`

Server → client:

```json
{"type": "hello", "version": "0.1.0", "operator": false, "session": "s-1a2b3c4d"}
{"type": "fleet", "data": { "...fleet snapshot..." }}
{"type": "event", "data": {"seq": 812, "kind": "ring_passed", "vehicle": "sim-1", "...": "..."}}
{"type": "error", "error": {"code": "not_claimed", "message_en": "...", "message_zh": "...", "detail": {}}, "ref": "sim-1"}
```

`fleet` arrives at 10 Hz, `arena` (the `GET /arena` view) at 20 Hz, and `event` as events happen. Client → server: `sticks` (above), `{"type": "fire", "vehicle", "on"}` (the controller's trigger, refreshed every 100 ms while held; 300 ms without a refresh releases it) and `{"type": "ping"}` (answered with `pong`). An invalid token closes the socket with code 4401; a disallowed browser origin closes it with 4403.

## 8. MCP servers

Relay ships three stdio Model Context Protocol servers (JSON-RPC 2.0, standard library only; protocol versions 2024-11-05 to 2025-11-25). Connect any one of them or all three:

| Server | File | Tools | Scope |
|---|---|---|---|
| `anet-relay` | `mcp/anet_relay_mcp.py` | 20 `relay_*` (13 at the `sticks` level) | Flight: fleet, claims, arm, mode, skills, plans, timed sticks, re-fly, courses, stop |
| `anet-relay-device` | `mcp/anet_relay_device_mcp.py` | 36 `device_*` | Device level: overview, MAVLink messages, parameter reads and writes, raw commands, single-motor tests, actuators, RC override, message rates, reboot, calibration, home, attitude and velocity control, flight termination, bench procedures and their reports |
| `anet-relay-app` | `mcp/anet_relay_app_mcp.py` | 42 `app_*`, 19 program tools and 4 dogfight tools | Application control: app and window state, controllers, language, workspace, selection, inspector, dialogs, screenshots, network scan, connecting and removing aircraft, simulators, settings, alerts, records and export, re-fly sources, possession, the Copilot window, stop-all; onboard programs: `program_guide`, `program_*`, `challenge_list`, `challenge_submit`, `job_status`, `duel_run`, `ladder`, `airframe_set`; dogfights: `dogfight_start`, `dogfight_stop`, `dogfight_status`, `leaderboard` |

Each server opens an agent session named by `--name` (defaults `mcp`, `mcp-device` and `mcp-app`) at start, renews its lease and closes it when the client disconnects. After a Relay restart it opens a new session on the next call; claims must then be made again. Claims belong to a session: fly an aircraft with the claim tool of the same server (`relay_claim` or `device_claim`). Arguments are checked before anything reaches Relay; missing or unknown ones come back as `invalid arguments`. Failures come back as tool results with `isError: true` and the error code, so a model can react (for example, wait on `possessed_by_human`).

The application server's tools work while `agents_app_control` is on; they need no operator token. `--operator-token` (or `RELAY_OPERATOR_TOKEN`) is only for calls made as the operator and is normally not needed.

The application server's program tools that act on an aircraft (`program_deploy`, `program_stop`, `program_resume`, `program_params`) claim it for that server's session; if the flight server's session holds the claim, release it there first (`relay_release_claim`). `program_deploy` with `arm: true` switches to a manual mode and arms before it deploys (a real aircraft also needs `confirm: "ARM"`).

## 10. Moving to a real aircraft

1. Set up the aircraft and its Wi-Fi bridge (`hardware.zh-CN.md`) and confirm it appears in the fleet as `real-<ip>`, for example `real-10-7-7-36`.
2. Complete the operator steps in the Relay window: verify stick directions without propellers, confirm propellers and the safety net, pass every blocking preflight item.
3. Replace the vehicle id in your code. Arming needs `confirm: "ARM"`. Position skills (`goto`, `rtl`, courses) need a local position source; without one, use `takeoff`, `hold`, `yaw`, `land` and open-loop `move` in altitude-hold modes, and expect the aircraft to drift slowly while it holds.
4. Keep an operator at the window. Possession and the stop button override any agent at any time.

## 11. Copilot (built-in agent)

The desktop app includes Copilot, a small agent built on [pi](https://github.com/earendil-works/pi) (`@earendil-works/pi-agent-core`). It runs in the app's main process and uses this API like any other agent: it opens a session named `copilot`, claims the aircraft it is asked to fly and appears in the Agents workspace and the relay timeline.

- **Floating window:** Copilot is a separate floating window that stays above other applications but is not modal: while it is shown you can keep clicking the Relay main window and any other application. Drag its title bar to place it anywhere on screen (including to the left of the main window) and its edges to resize it; position and size are remembered. The Copilot button in the top bar, Ctrl/Cmd + J or the window's own hide button shows or hides it. Each message carries the aircraft selected in the main window.
- **Setup:** Settings → Copilot: interface type (`openai-completions` for OpenAI-compatible endpoints, also `anthropic-messages` and `openai-responses`), base URL, model ID, API key, tool scope and window opacity (60–100 %). **Test connection** sends one short request. The key is stored in the app data directory (`copilot-secrets.json`, AES-256-GCM with a random per-installation key in `copilot-secrets.key`, both readable only by your user account) and never returns to the interface; the endpoint receives only the conversation and tool results. **Store keys in the system keychain** (off by default) keeps the key in the macOS Keychain, Windows credential encryption or the Linux Secret Service instead; only then does Relay call Electron `safeStorage`. Relay never reads or needs your system login password: a keychain dialog comes from the operating system and appears only when you choose the keychain. A key saved by 0.3 or earlier stays in the keychain untouched until you either enter it again or choose **Keep using keychain** in the Copilot window.
- **Tool scope:** `flight` (status, skills, plans, timed sticks, re-fly, stop), `flight+device` (adds the device-level tools) and `all` (the default; adds application control: language, workspace, selection, network scan, simulators, settings, controllers, records, window and screenshots). The tools map one to one onto the endpoints of section 5.
- **Safety:** every motion command and device write on a real aircraft (take-off, move, turn, hover, land, plans, re-fly, motor tests, actuators, reboot, calibration, termination and others) shows an approval card in the chat, and nothing is sent until the operator approves (120 s without an answer counts as declined); the floating window shows itself and flashes when an approval is waiting. The approval stands in for the confirm word; Copilot never fills one in on its own. Possession and stop work on Copilot exactly as on any other agent.
- **Programs and the flight level:** Copilot reads `agent_flight_level` before every message. At `sticks` (the default) it has no take-off, move, turn, hover, plan or re-fly tools and its instructions say that high-level flight is unavailable and that stable flight needs a program; at `full` it has them again. In every tool scope it has the program tools (`program_list`, `program_get`, `program_create`, `program_update`, `program_validate`, `program_test`, `program_deploy`, `program_stop`, `program_resume`, `program_params`, `program_status`, `program_log`, `challenge_list`, `challenge_submit`, `job_status`, `duel_run`, `ladder`, `airframe_set`) plus `relay_arm`, `relay_disarm` and `relay_mode`, and its instructions end with [`programs-guide.md`](programs-guide.md). Writing and editing programs needs no approval; deploying or resuming a program on a real aircraft, arming it and changing its mode wait for the operator's approval like every other motion.
